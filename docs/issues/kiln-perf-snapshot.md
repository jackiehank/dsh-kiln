# kiln-perf-snapshot — 一次快照的延迟从哪来

## 问题

视图打开要等一次快照。快照的构成是**一个 issue 一个 `kiln path`**：

```text
kiln graph --json            1 次
kiln path <id> --json        N 次（N = min(issue 数, 80)）
```

本仓 18 条 issue → 19 个子进程；`~/kiln` 59 条 → 60 个。子进程在 Windows 上主要花在**进程启动**上
（`kiln --version` 与 `git rev-parse HEAD` 都在 80ms 量级，`kiln path` 只多 20~30ms 的实际工作）。
所以冷启动的量级天然是「N × 100ms ÷ 并发」。

缓存已经把「重复打开」这一半解决了：HEAD 不动时命中只要 0.6ms，切页回来也不卡。剩下两处仍然要等：

1. **冷启动**：应用重启后第一次打开（进程内缓存是空的）；
2. **HEAD 动过之后**：每提交一个动作，下一次打开要多花一次 `graph` + 几条 git 探测 + 受影响
   issue 的 `path`，量级 0.4s。

用户口径即「首次打开顿一下、提交后刷一下也要等一下」，交互与语义都已经稳了，这一轮只处理延迟。

## 目标

1. 冷启动：本仓（18 条）≤ **600ms**，`~/kiln`（59 条）≤ **1.4s**；
2. 单条新提交后的刷新 ≤ **300ms**；
3. 同一仓库的并发请求**只跑一次构建**（连点刷新不该把 60 个子进程跑两遍）；
4. 命中路径保持 ≤ 5ms；
5. 延迟可观测：头部快照提示能直接看到「这次是 build / 增量 / 命中，花了多少毫秒」，
   不用开控制台。

## 边界

- **仍然只读**：数据只来自 `kiln <cmd> --json`；git 只用来判断「该重取谁」，不用来推导状态
  （沿用 `kiln-views-shared-focus` 的约定）；
- **不落盘**：不写缓存文件，拔掉插件仓库零残留这一条不破。跨重启的持久化缓存是另一个问题，
  要另开 issue，并且先确认宿主有没有给插件的用户数据目录；
- **不加轮询**：延迟不能靠后台多跑来掩盖；
- **不改视图语义**：这次只动宿主侧的取数与请求调度，三个页面、筛选、搜索的行为不变；
- 上限仍是 80 条 issue（`DEFAULT_MAX_ISSUES`），不因为性能改截断策略。

## 验收

- 有一个可复跑的探针（提交进仓库），能一次打出：graph 耗时、冷启动、命中、单条 `path`、
  并发扫描、快照体积；
- 两个仓各跑一遍，冷启动与增量达到目标；
- 连点两次刷新时宿主只起一轮子进程（构建合并）；
- 宿主侧新增用例覆盖「并发合并」与「并行探测」，现有 45 + 45 用例全过；
- 前端侧不动取数协议（除响应头多一个耗时字段），渲染用例不变。

## 现状（沿用已记录的事实）

| 事实 | 数字 | 出处 |
| --- | --- | --- |
| `kiln path <id> --json` 单条 | ~100–110 ms | `kiln-views-shared-focus` collect 2 |
| `kiln graph --json` | ~102 ms | 同上 |
| `~/kiln` 58 条全量 @并发 4 | ~1.6 s | 同上（当时已判定「成本几乎全在 path」） |
| HEAD 命中 | ~2 ms（直读 ref）/ 单次请求 <1 ms | 同上 |
| 增量刷新的子进程 | 1 次 git range + 1 次 graph + 受影响 issue 的 path | 同上 |

这几条只说明"钱花在哪"，具体到今天的机器、并发曲线与前端成本，见 collect。

## 收集：今天的实测

环境：Windows 11 · 20 逻辑核 · Node v24.19.0 · kiln 0.1.1（`C:\Users\jacki\go\bin\kiln.EXE`）。
探针随仓库提交，可复跑：

```powershell
node plugin/test/probe-perf.mjs . C:\Users\jacki\kiln
```

两个仓：`dsh-kiln`（18 issue / 104 动作）、`~/kiln`（59 issue / 257 动作）。

### 一次快照

| 仓库 | issue | `graph` | 冷启动 | 快照 JSON | HEAD 命中 |
| --- | --- | --- | --- | --- | --- |
| dsh-kiln | 18 | 115 ms | **696 ms** | 39 KB | 0.7 ms |
| `~/kiln` | 59 | 108 ms | **1924 ms** | 87 KB | 0.6 ms |

冷启动 ≈ `graph` + `ceil(N / 4) × 110ms`，与「成本几乎全在 path」的旧结论一致；
命中路径已经只剩一次直读 HEAD，没有可压的空间。

### 并发扫描（一次重建里跑完全部 `kiln path`）

| 并发 | 2 | **4（今天）** | 8 | 12 | 16 | 24 |
| --- | --- | --- | --- | --- | --- | --- |
| 18 条 | 958 ms | **558 ms** | 430 ms | 439 ms | 420 ms | 437 ms |
| 59 条 | 3259 ms | **1819 ms** | 1258 ms | 1264 ms | 1240 ms | 1256 ms |

8 之后是平台期：Windows 的进程创建在 8 个并发时就打满了，再加只是把等待切得更碎
（59 条 8→24 只差 18ms，噪声级）。**并发 4 是被丢掉的 30%。**

### 进程启动地板（5 次中位数）

| 命令 | 耗时 |
| --- | --- |
| `kiln --version` | 84 ms |
| `git rev-parse HEAD` | 82 ms |
| `git merge-base --is-ancestor` | 86 ms |
| `git log -n 50` | 88 ms |

单条 `kiln path` 是 104–110 ms，即**其中约 80ms 是启动**，真正干活只占 20–30ms。
推论：只要还是「一条 issue 一个进程」，冷启动的物理下限就是 `N × 80ms ÷ 并发`。

### 增量刷新（在一次性克隆里提交一条动作后测）

| 步骤 | 耗时 | 缓存 |
| --- | --- | --- |
| 冷启动（克隆） | 682 ms | `build` |
| 提交一条动作后再刷新 | **329 ms** | `incremental`，只重取 `kiln-search` |
| 紧接着再刷新 | 0 ms | `hit` |

329 ms 由四个子进程构成，但它们的依赖关系并不成立：

```text
readGraph（108）→ isAncestor（86）→ newIssueIds（88）→ path × k（110）
```

`graph`、`merge-base --is-ancestor`、`git log <old>..<new>` **三者互不依赖**——现在却排着队跑。

### 前端纯计算（85 KB 快照，5 次中位数）

| 操作 | 耗时 |
| --- | --- |
| `JSON.parse` | 0.20 ms |
| `searchIssues`（全仓 257 个动作） | 0.15 ms |
| `buildMermaid`（59 节点） | 0.02 ms |

前端不是瓶颈：解析、搜索、mermaid 文本都在 1ms 以下；真正花时间的是 pele 的布局与绘制，
那条线已单独量过（58 节点约 20ms，`kiln-graph-readability`），这次不动。

### 结论

1. 主成本是 **N 次进程启动**，不是数据量（87 KB 解析 0.2ms）；
2. 并发 4 → 8：冷启动 −23%（18 条）/ −31%（59 条），再高无收益；
3. 增量刷新的四个子进程里有三个**互不依赖**，串行是白等；
4. 前端、payload、命中路径都不值得动。

## 假设：把"启动次数"和"排队"分开治

### A. 并发 4 → 8（做）

依据表 2：8 是平台期起点（59 条 1819 → 1258ms，−31%；18 条 558 → 430ms，−23%），
再往上 12/16/24 只差 6~24ms，是噪声。

不做「按 CPU 自适应」：本机 20 核，自适应会取到 16+，而实测那里没有收益，
反而在别人的 4 核机器上会开得太多。**8 是"小仓不浪费、大仓打满"的折中**。

### B. 增量刷新并行化（做）

`graph`、`merge-base --is-ancestor`、`git log <old>..<new>` 三者互不依赖，一起发：

```text
max(graph 108, isAncestor 86, newIssueIds 88) + path × k
≈ 108 + 110k        （今天：108 + 86 + 88 + 110k = 392 + 110k）
```

单条新提交 329 → ~220ms。

取舍与风险：

- 三路里 `newIssueIds` 在「不是祖先」时白跑一次（88ms）——但它是并行的，白跑不占墙钟；
- 「增量不可用就全量」的语义必须保持：非祖先、`delta.ok === false`、graph 失败都要能落到重建，
  而且**不能**把先前那次的 graph 结果当成必然可用（失败要能重试）；
- graph 结果要能传进 `buildRecord`，否则增量分支会第二次调 `kiln graph`（白花 108ms）。

### C. 单飞：同仓并发请求共享一次构建（做）

今天连点两次刷新会跑两轮 60 个子进程。做法：按 `repo + maxIssues` 记 in-flight promise，
第二个请求等同一个构建；**只在构建结果的 `head` 与本次探测一致时复用**，否则走自己的判断。
失败结果不粘（不进 store，也不留在 in-flight 里当答案）。

预期：连点刷新从 2×1924ms 变成 1924ms + 0ms。

### D. 渐进两段快照：graph 先回、动作后补（否决）

- 收益在观感：首屏从 1.9s 变 0.3s；
- 否决理由：默认页是**时间线**，第一屏没有动作行会"先空后跳"，比等一秒更糟；
  而且要把"局部快照"的合并语义带进客户端、缓存与失效判断——契约变复杂，收益却只是观感；
- 等 F 落地后一次请求就够快，渐进没有存在意义。

### E. 跨重启持久化缓存（否决，另开 issue）

把 `{repo, head, configToken, binToken, payload}` 写进宿主用户目录，重启后 HEAD 一致就直接用，
冷启动 1.9s → 0ms。否决理由：破了「不落盘」；宿主有没有给插件的用户数据目录还没确认；
而且它只优化"重启后第一次"这个低频事件。先记账。

### F. 上游：一次取全仓动作（提 issue，不等）

`kiln path a b --json` 今天**静默忽略第二个 id**（exit 0，只回第一个），所以只能 N 次启动。
若上游支持 `kiln path --all --json`（或接受多个 id），冷启动 ≈ 1 次 path ≈ 150–200ms，
A/B/C 就都成了余量。给 `~/kiln` 提 ask，并与 `issue-list-scaling` 关联。

### 决定

本轮**落地 A + B + C**；D/E 否决并记账；F 提上游。另外补一个观测口径：
构建耗时进 `payload.cache.ms`，头部快照提示直接显示，便于以后复核不用开控制台。
