# DSH 的「安装插件」装不出真插件：仓库根没有 package.json

## 背景

用户在 dsh-desktop 的点选安装界面（「安装插件」）里填了本仓库地址，结果是：

```
+ dsh-kiln 0.0.0
```

依赖名是 `dsh-kiln`、版本 `0.0.0`，而真包叫 `@jackiehank/dsh-kiln`、版本 `0.15.0`。

## 现状（读出来的事实）

- 安装走的是 GitHub **仓库根 tarball**：
  `https://codeload.github.com/jackiehank/dsh-kiln/tar.gz/f69be84…`（1.9MB，整个仓）。
- 仓库根**没有 `package.json`**（插件包在 `plugin/`），pnpm 于是写了一封占位文件：
  ```json
  {"_pnpmPlaceholder":"This file was generated by pnpm. The original package did not contain a package.json."}
  ```
  依赖因此被记成 `dsh-kiln@0.0.0`，既没有 `dsh.bundle` 也没有 `exports` —— 装了个空包。
- 它还**重写了 profile 的 manifest**：21:47 用 tgz 装好的 `@jackiehank/dsh-kiln 0.15.0`
  （在 `dependencies` 与 `dsh.profile.bundles` 里都有）在 22:12 之后消失了。

## 目标

1. 「粘仓库地址 → 安装」这条路要能装出**真插件**；否则 UI 至少得**明确拒绝**并指路 tgz，
   而不是静默装一个 `0.0.0` 空包。
2. README 里「直接从仓库装」的说法要和 UI 的实际能力对齐。

## 边界

- 不改插件运行时行为；只动仓库形态与文档。
- 任何根级 manifest 都必须与 `plugin/package.json` 的名字 / 版本一致，并有测试守住（防漂移）。

## 收集：本轮实测

| 观察 | 证据 |
| --- | --- |
| UI 走 codeload 根 tarball | `.plugin-manager/logs/operation-adKubO/pnpm.log` 里的 URL |
| 根没有 manifest → 占位文件 | `node_modules/dsh-kiln/package.json` 内容就是 `_pnpmPlaceholder` |
| 依赖名/版本失真 | `dependencies: + dsh-kiln 0.0.0` |
| manifest 被重写 | 21:47 的 tgz 安装条目在 22:12 之后从 `package.json` 与 `bundles` 里消失 |
| UI 能跑 git | `.plugin-manager/logs/github-connection-*/git.log`（0 字节 = 无报错） |
| 本沙箱无法实测 `#path:` | `dsh plugin add 'github:…#path:/plugin'` → `ERR_PNPM_GIT_RESOLVE_FAILED … spawn EPERM`（沙箱禁止 Node 派生 git） |
| 桌面 profile 不能 CLI 组合 | `dsh --profile desktop --dump-config` → `profile "desktop" is managed exclusively by the Electron application` |

**已修**：删掉占位包，用 `plugin/jackiehank-dsh-kiln-0.15.0.tgz` 重装，`dependencies` 与 `bundles`
都回到 `@jackiehank/dsh-kiln 0.15.0`。（本节只解决眼前，不解决「UI 安装」这条路。）

## 方案（hypothesize）

### A. 仓库根放一个转发 manifest（推荐）

根 `package.json`：同名同版本、`private: true`（防误发 npm）、`exports` 与 `dsh` 全部指向 `plugin/`：

```json
{
  "name": "@jackiehank/dsh-kiln",
  "version": "0.15.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./plugin/lib/index.js", "./client": "./plugin/lib/client.js" },
  "dsh": { "bundle": { "patch": "./plugin/cordis.patch.yml" }, "client": { … } },
  "files": ["plugin/lib", "plugin/locale", "plugin/icon.svg", "plugin/cordis.patch.yml"]
}
```

- 好：`github:owner/repo` 能装出真包；不动 `plugin/` 的目录结构；不发 npm。
- 代价：**两份 manifest 要同步**（名字 / 版本 / `dsh` 字段），必须加测试；
  `private: true` 让根永远不能被 npm publish（正确，发的是 `plugin/` 那份）。

### B. 把 `plugin/` 提到仓库根

结构最干净，但 workflow 的 `working-directory: plugin`、几十份文档路径、测试相对路径全要改，
且本仓的 `docs/`、`AGENTS.md` 会混进包目录。否决（这一轮）。

### C. 只支持 tgz，把 UI 那条路写死

零改动，但用户第一次接触就是「装了个 0.0.0」——这是**静默失败**，最差的体验。可以接受的前提是
UI 自己会拒绝；我们控制不了 UI，所以至少 README 要写清「点选安装不支持，用 tgz」。

### D. 发 npm

`dsh plugin add @jackiehank/dsh-kiln` 最短，但没账号，且不影响 A / C。

### 决定

**A + C 文案**：先让 `github:owner/repo` 装得出真包（A），README 里同时把「点选安装 / tgz / `#path:`」
三条路的实际能力写清楚（C 那半只做文案）。

## 落地清单（apply 时）

- 新增根 `package.json`（`private: true`，`exports` / `dsh` / `files` 转发到 `plugin/`）。
- `plugin/test/run.mjs` 加一例：根 manifest 与 `plugin/package.json` 的 `name` / `version` / `dsh.bundle.patch`
  一致；根 `private` 为真。
- 根 README 的安装段：把「点选安装」写成**当前不支持**（会装成 `dsh-kiln@0.0.0`），tgz 仍是主渠道；
  `#path:` 规格保留为「命令行可用」。
- `plugin/README.md` 同步一句。

## 落地（apply）：根 manifest + 0.15.1

**先确认了一件事**：`v0.15.0` 的 Release 已经发出去了（资产 347,411 B，与本地 `npm pack` 一致），
所以修好的形态不能塞回 0.15.0——版本升到 **0.15.1** 再发。

改动：

| 文件 | 内容 |
| --- | --- |
| `package.json`（根，新增） | `name` / `version` 与插件一致，`private: true`，`exports` 与 `dsh.bundle.patch` / `dsh.client` 全指向 `plugin/` |
| `plugin/package.json` | `version` → 0.15.1 |
| 根 `README.md` | 安装段改成「从 GitHub 直接装」（与点选界面同一条路），保留 `#path:` 与本地 checkout；开发目录树加根 manifest |
| `plugin/README.md` | 版本行 0.15.1 + 新增一段说明；安装段同步 |
| `plugin/test/run.mjs` | 新增一例：两份 manifest 的 `name` / `version` / `dsh.bundle.patch` / `dsh.client` / `engines` 必须一致，根 `private` 为真，转发路径必须真实存在 |

验证（都在本机）：

- `npm test --prefix plugin` → **87 + 63**；
- 根目录 `npm pack` → `jackiehank-dsh-kiln-0.15.1.tgz`，**17 个文件**（多出来的那个是根 `README.md`，
  npm 自动带上）；
- 装进沙箱 profile（`DSH_HOME=.tmp-dsh-home`）后 `dependencies` 是 `@jackiehank/dsh-kiln 0.15.1`，
  包内能看到 `plugin/lib/client.js`、`plugin/cordis.patch.yml`（insert 行 `id: dsh-kiln`）——
  也就是说 `github:owner/repo` 那种「整仓 tarball」装法能装出可用的包了。

**没验到的**：DSH「安装插件」界面本身（要等 0.15.1 推上去、tag 发版后再点一次）；
`#path:` 规格在本沙箱测不了（`spawn EPERM`）。

**代价**：两份 manifest 要同步——`name` / `version` / `dsh` 任一处漂移都会被那条新用例打回。
根那份永远 `private`，npm 仍然只发 `plugin/`。
