# kiln-cache-budget — 动作流缓存的容量默认值：总预算而不是每仓乘法

## 问题

动作流缓存现在有两条上限，宿主与客户端各一份：

- `plugin/lib/rowsCache.js:26` `ROWS_LIMIT = 50_000`、`:27` `BYTES_LIMIT = 20MB`，`:29` `REPO_LIMIT = 2`；
- `plugin/lib/client.js:72` `TIMELINE_CACHE_ROWS = 50_000`、`:73` `TIMELINE_CACHE_BYTES = 20MB`。

容量是按**每仓**给的，而 `REPO_LIMIT = 2` 让它变成**乘法**：两个大仓就是 2 倍。

后果在 100k 动作的仓上最明显：整条流约 **26MB**、10 万行，两条上限都越界，两端都判 `oversize`，
之后每次挂载都全量流式（暖读 166ms + 26MB 传输 + 53ms 解析 + 28ms 折叠 ≈ 0.25–0.3s），**每次都要付**；
而一个 100k 仓其实完全值得驻留——HEAD 不变时切页本该 0 字节。

抬高上限又会撞另一头：宿主是 DSH 服务进程，**长命、跨会话共用**；浏览器标签是另一个进程。
按已测的每行成本，100k 行两端合计约 100MB+/仓，两仓就 200MB+。默认值定错，用户要么慢，要么卡。

## 已有的证据（2026-10-30 实测）

本仓 170 行，克隆到 10 万行后测（`node --expose-gc`，与 `plugin/test/probe-memory.mjs` 同一套方法）：

| 项 | 数字 |
| --- | --- |
| NDJSON 体积 | 100k 行 **26.1MB**（本仓 399B/行） |
| rows 常驻堆（宿主形态） | 322 B/行（克隆共享了部分字符串；真实约 400 B/行 → ~40MB） |
| rows + fold 常驻堆（客户端形态） | 502 B/行 → ~50MB（fold 171 B/行，15.9k issue） |
| parse / fold / stringify（100k） | 53ms / 28ms / 68ms |
| 首次构建峰值 | 探针 170MB（含 stringify 副本；真实流式会低一些） |
| 现行绕过时的每次挂载 | kiln 暖读 166ms（上游 v0.4.0 数字）+ 26MB + parse 53ms |

上游 v0.4.0 之后读耗时与仓大小无关（本仓 36ms、`~/kiln` 36ms，都在 node 起进程地板），
所以容量问题**只剩内存与传输**，不再有“读得太慢”这一项。

## 约束

- **不给用户配置项**：不新增环境变量、不加设置 UI。默认值要按测得的事实自适应；
  唯一的“关断”仍是已有的 `DSH_KILN_TIMELINE_CACHE=off`（诊断用，不是常规配置）。
- 不落盘（与整仓一致）；不做跨进程共享内存。
- 宿主与客户端各自独立计算，不要求两边同一时刻做同一决定（现有 `hit/unchanged/…` 协议不变）。
- 只读，不碰上游；分页/索引已由 `kiln-many-issues` 判为不做。

## 要回答的问题

1. **“够用”怎么定**：一台机器通常同时开几个 kiln 仓？宿主多留 40–80MB、浏览器多留 50–100MB 可接受吗？
2. **容量表达**：从“每仓上限 × 仓数”改成“**总预算，跨仓 LRU**”？预算取多少——
   固定值（如 128MB）、还是按 `os.totalmem()` 比例（不配置也算自适应）？
3. **超预算时的降级**：淘汰最旧仓、还是把小仓也降级？必须是“少缓存”而不是“报错/空页”。
4. **要不要先做紧凑存储**：`short`/`action`/`domain` 大量重复，驻留或打包能把 400B/行压到 ~250B/行，
   省下的是内存而不是代码；值不值得为它改 rows 形状（会影响 `delta` 合并与测试）？
5. **峰值控制**：流式构建时的临时对象、以及客户端每批 `foldIssues` 为 O(n)（10 万每批约 50ms，
   已在 backlog）要不要一起处理？
6. **与增量门槛的配合**：100k 仓保留 5 万行以上时，`incremental` 的 5000 行门槛与 2000 提交上限
   是否仍合适？

## 非目标

- 不做用户可见配置（环境变量、设置页、配置文件都不加）。
- 不做分页 / 截断输出（上游 `issue-list-scaling` 已否决 `--limit`）。
- 不做持久化缓存。
- 不改变现有缓存协议（`hit/unchanged/incremental/delta/bypass`）与安全判定。

## 验收

- 用 100k 行 fixture 直接喂宿主 handler（不必造 10 万提交的 git 仓）：首次流式 ≤0.4s；
  HEAD 未变时挂载 **0 字节**；两端常驻不超过设定预算。
- 两个 100k 仓来回切：总常驻不超预算，淘汰可观测（`stats` 有记录），不出现空页/错误。
- 小仓（本仓 170 行）：行为、内存、首屏与现在一致，缓存命中路径不变。
- 单仓超过总预算：该仓单独降级为每次流式，**另一个仓的缓存不受影响**。
- `run.mjs` / `render.mjs` 覆盖：预算淘汰、单仓超限降级、两仓并存、100k fixture 的往返正确。
- 文档写明默认预算值与理由（数字来自探针，不是拍的）。

## collect（2026-10-30）：现在缓存里到底存的是什么形状

复现：`node --expose-gc plugin/test/probe-format.mjs`（把真实行克隆到 10 万行，逐变体 gc 后取堆增量）。

### 1. 两端各存一份

- **宿主**（`rowsCache.js:73`）：`repo → { head, configToken, binToken, rows, bytes }`；
  `rows` 是 `mapActionRecord()`（`timeline.js:46`）产出的 **8 键对象**数组：
  `issueId / action / id（40 位）/ short（7 位）/ date（25 字符）/ title / domain / tags[]`。
  命中时逐行 `JSON.stringify({ kind: 'action', ...row })` 重发（`timelineHandler.js:218`），
  `bytes` 记的是**线上字节**，不是堆占用。
- **客户端**（`client.js:80`）：`timelineCache` 再存同一批行对象；另外 `foldIssues` 为每个动作
  **另建一个对象**塞进 `issue.actions`（`client.js:1054`）。所以浏览器里是 rows + fold 两半。

### 2. 100k 行实测矩阵

数据分布：171 条真行 → 28 issue / 6 个动作 / 2 个 domain / 14% 行带 tags；平均 title 51.6 字（中文）、
id 40、date 25、issueId 18.6。克隆后每行 id/title/date 唯一，其余文本重复（与真仓同形）。

| 变体 | 常驻堆 | B/行 | build | serve（每次重发） | 线上字节 |
| --- | --- | --- | --- | --- | --- |
| A 现状：8 键对象 | 47.6MB | 499 | 50ms | 74ms | 31.9MB |
| B 去 `short`、空 `tags`→null | 41.9MB | 439 | 54ms | 76ms | 32.0MB |
| B2 B + 驻留 issueId/action/domain（tags 存串） | 31.6MB | 331 | 66ms | 67ms | 32.1MB |
| B3 B + `date` 存 epoch 毫秒 | 37.6MB | 395 | 68ms | 129ms | 32.0MB |
| C B2 + B3 | 28.5MB | 299 | 77ms | 126ms | 32.0MB |
| D 数组行（7 槽） | 30.8MB | 323 | 85ms | 125ms | 32.0MB |
| F 列式（7 条平行数组） | 24.7MB | 259 | 83ms | 126ms | 32.0MB |
| G 数组行 + **数组线上格式** | 30.8MB | 323 | 82ms | **58ms** | **22.2MB** |
| E 原始 NDJSON 行（JS 字符串） | 51.6MB | 541 | 27ms | 16ms | 28.8MB |
| H 原始字节（Buffer/行） | external 29.6MB + heap 10.8MB | 302 | 53ms | ≈0 | 22.9MB |
| H2 原始字节（一整块 Buffer） | external 28.8MB | 302 | 41ms | ≈0 | 22.9MB |

### 3. 归因（哪一刀最值）

- **驻留重复串**是最大的一刀：B→B2 **−108B/行**（28 个 issueId、6 个 action、2 个 domain 的重复文本
  在 10 万行里各占一份独立字符串对象），且 serve 不变（67ms 比 B 还略低）。
- 去 `short`（可由 `id` 推出）+ 空 `tags` 数组换 `null`：B−A **−60B/行**；86% 的行 tags 为空。
- `date` 换数字：**−44B/行**，但 serve **+55ms**——每次重发都要 `new Date(ms).toISOString()`。
- 数组行/列式再省 30–70B/行，但访问方式从字段名变成下标。
- **原始 NDJSON 当 JS 字符串存是最差选项**（541B/行）：含中文的行在 V8 里按两字节/字符存，
  240B 的字节行变成 ~480B 的字符串 + 头。这也印证了 `rowsCache.js:10` 的注释（不存原文）。
- 但**存字节**（Buffer）只要 22.9–29MB、serve≈0；代价是宿主不再持有可读行——增量判定要用的
  `boundary.id` / `boundary.date`、行数、HEAD 得另存，delta 也要按字节拼。

### 4. 客户端是双份：rows + fold

`foldIssues` 为每个动作建对象并复制字段（`client.js:1054-1063`），100k 行约 **14MB / 147B 行**（34ms）。
所以浏览器总占用 ≈ rows + fold：

- 现状：499 + 147 ≈ **646B/行 ≈ 63MB**（100k）；
- 只做 rows 紧凑（C）：299 + 147 ≈ 446B/行 ≈ 44MB；
- 若 rows 与线上都换数组（G）：同样 44MB，但线上 22.2MB（−31%）、重发 58ms（−16ms）。

### 5. 迁移面（形状一变全要跟）

- 客户端 3500 行里：`.id` 76 处、`.action` 26、`.title` 16、`.date` 15、`.domain` 12、
  `.issueId` 11、`.tags` 6；`mergeTimelineRows` 按 `row.id` 去重（`client.js:94`）；
- 增量判定读 `boundary.id` / `boundary.date`（`rowsCache.js:157-184`）；
- `foldIssues`、筛选、搜索跳转、渲染都按字段名取；
- 宿主 `timelineHandler` 的逐行 stringify；`run.mjs` 的 fixture payloads、`render.mjs` 的行对象。

### 6. 候选方向（留给 hypothesize 选）

1. **只紧凑行内**（驻留 + 去 short + tags 串 + date 数字）：499→299B/行（−40%），协议不动；
   serve 每次多 50ms，但只在 HEAD 变化时付。
2. **协议一起换数组**：G，323B/行、线上 −31%、serve 58ms；接口面与测试改动最大。
3. **宿主只存字节**：H，宿主内存 −40%~−50%、serve≈0；客户端仍解析成紧凑行；
   宿主不再有“行”，增量/delta 要重新设计边界。
4. **不做行紧凑，改 fold 增量**：省的是 CPU（每批 O(n)），不减常驻。

### 7. 与本文目标的关系

紧凑化要回答的是：**默认值能不能覆盖 100k**。以现状算，两端合计约 130MB/仓（63 宿主 + 63 浏览器）；
只做方向 1 降到约 90MB/仓；方向 3 能把宿主那半压到 30MB 左右，浏览器那半仍取决于 rows 形状。

## 假设（2026-10-30）：选 G2——7 槽数组，宿主与客户端同形，线上也发数组

### 1. 形状定义

```text
ROW = [issueId, action, commit, date, title, domain, tags]   // 下标 0..6
```

- `short` 不存：`commit.slice(0, 7)`，只对**可见行**和详情调用（虚拟列表下每屏约 30 行）；
- `tags`：空为 `null`，否则 `tags.join('\u0001')`（标签是 kebab 词，不含控制字符）；渲染时再 `split`；
- `date` 保持 RFC3339 **原串**：offset 是语义的一部分，kiln 契约明确「保留提交自己的 offset」；
- `issueId` / `action` / `domain` 过**驻留池**（`Map<string,string>`，随缓存条目存），delta/增量追加时复用；
- 线上：一行一个数组（`[…]`）；事件仍是对象（`{kind:'done'}` / `{kind:'error'}`），按首字符 `[` / `{` 分流。

### 2. 为什么是 G2，而不是 G

G（`date` 存 epoch 毫秒）省 32B/行，但把「提交自己的 offset」丢了：`date.slice(0,10)` 是插件显示日期的
唯一来源，+13:00 的提交按本地时区渲染会差一天；而且要重建 ISO 串还会让重发从 56ms 涨到 ~125ms。
**否决 G 的 date 数字，取 G2（date 原串）**——牺牲 32B/行，换语义不变与 54ms 重发。

### 3. 与其它方案的实测对比（100k 行，均含驻留）

| 方案 | 常驻 | 100k 常驻 | 线上 | 宿主重发 | 客户端收行 | 迁移面 |
| --- | --- | --- | --- | --- | --- | --- |
| A 现状（8 键对象） | 499B/行 | 47.6MB | 31.9MB | 74–76ms | 60ms | — |
| B2 对象 + 驻留 | **332B/行** | **31.6MB** | 32.1MB | 68–70ms | 60ms | 小 |
| C 再换 date 数字 | 300B/行 | 28.6MB | 32.0MB | 125ms | 60ms | 小中 |
| F 列式 7 数组 | **260B/行** | **24.8MB** | 32.0MB | 128ms | 60ms | 大（列式→行） |
| G 数组 + date 数字 | 324B/行 | 30.9MB | **22.3MB** | **56–60ms** | **43ms** | 大 |
| **G2 数组 + date 原串** | 356B/行 | 33.9MB | **23.6MB** | **54ms** | **43ms** | 大 |
| H 宿主存字节（Buffer） | 302B/行 | 29.6MB 外 + 10.8MB 堆 | 22.9MB | ≈0 | 43ms | 最大 |

**要点：G2 不是内存方案。** 数组比同槽对象多 ~24B/行（V8 元素存储 + 数组头），所以它比 B2 多 2.3MB、
比 F 多 9MB。G2 的账在另外三栏：

1. **传输 −26%**（31.9 → 23.6MB）：省掉每行的键名与派生的 `short`；
2. **宿主重发 −22ms、客户端收行 −17ms**：宿主存的数组**就是**发出去的字节（`JSON.stringify(row)`），
   客户端 `JSON.parse` 出来的**就是**要存的行，两端都没有「再建一个对象」的转换层；
3. **一份形状走到底**：宿主缓存、线上、客户端缓存、fold 输入全同形。现状两端各建一次对象
   （宿主 `mapActionRecord`、客户端 `take()`），G2 把这两次都消掉。

### 4. 预算与默认值提案（不给用户配置）

按 G2 的账（每仓：宿主 34MB、浏览器 rows 34MB + fold 14MB = 48MB）：

- 单仓上限：**120k 行 / 32MB 线上字节**（100k 仓留 20% 余量；32MB 是按 G2 线上 23.6MB 的两倍取整）；
- **总预算：宿主 128MB、浏览器 128MB**，跨仓 LRU 淘汰（先淘汰最久没访问的仓，**单仓超预算只降级它自己**）；
- 自适应只用机器信息，不给配置项：宿主 `os.totalmem()`、浏览器 `navigator.deviceMemory`；
  内存 <8GB 时降到 64k 行 / 总预算 64MB，其余用上面默认值；
- 两个 100k 仓并存：宿主 68MB、浏览器 96MB，都在预算内；三个仓就开始按 LRU 淘汰。

### 5. 落地分步

1. **协议**（`timelineHandler.js`）：动作行改为 `JSON.stringify(row)`；`done` / `error` 不变；
   客户端带 `?format=2`，不带就返回 400 并提示刷新（旧客户端看到明确错误，而不是静默空列表）。
2. **客户端**：加 `ROW` 常量与 7 个访问器；替换 ~150 处字段访问；`foldIssues` 改下标；
   `mergeTimelineRows` 按 `row[ROW.COMMIT]`；渲染 / 筛选 / 搜索跳转。
3. **缓存**：条目存 `{ head, tokens, rows, bytes, pool }`；增量 boundary 读 `[ROW.COMMIT]` / `[ROW.DATE]`；
   客户端 `timelineCache` 同形。
4. **预算**：`rowsCache` 增加总预算与 LRU 淘汰（目前只有 `REPO_LIMIT`）；客户端同。
5. **测试**：`run.mjs` 的 payloads、`render.mjs` 6 处 fixture、增量 boundary 断言。

### 6. 风险

- **下标错位是静默的**（`row[1]` 本该是 action 却读了别的槽）：全部用常量；`__DSH_KILN_TEST__` 下加
  `assertRow` 校验长度/类型，渲染用例覆盖。
- **旧客户端**：不带 `format=2` 的请求直接 400；宿主与客户端同包发布，正常不会分叉。
- **tags 分隔符**：`\u0001` 不在 kiln 标签里，但要在文档与测试里钉死。
- **fold 仍复制一份（147B/行）**：G2 不解决它；要再省得做 fold 增量或懒折叠，另开。
- **别把 G2 当省内存方案宣传**：它比 B2 多 24B/行，省的是传输与两次对象构造。

### 7. 验收 / 实验

- `node --expose-gc plugin/test/probe-format.mjs` 的 G2 行可复现（356B/行、23.6MB、54ms、43ms）；
- 100k fixture 喂宿主 handler：wire ≤24MB、serve ≤60ms、宿主 heap ≤36MB；
- 本仓 172 行：三页行为不变，`render.mjs` 58 用例全过，`run.mjs` 更新后全过；
- delta / 增量结果与全量按 sha 集合和顺序逐一比对，无重复、无丢行；
- 两个 100k 仓来回切：总常驻在预算内，淘汰可观测，另一个仓不受影响。

## 落地（2026-10-30）：G2 行形状 + 固定预算

### 1. 改了什么

- `plugin/lib/timeline.js`：新增 `ROW` / `ROW_WIDTH` / `TAGS_SEPARATOR`、`rowShort` / `rowTags` /
  `createRowInterner`；`mapActionRecord` 改为返回 **7 槽数组**。
- `plugin/lib/timelineHandler.js`：行按数组原样写（`JSON.stringify(row)`）；新增 `?format=2` 门，
  不带就 **400 `format-required`**（旧客户端报“刷新”，不给假空列表）；构建与增量都过驻留池，
  池随缓存条目存；增量 boundary 读 `ROW.COMMIT` / `ROW.DATE`。
- `plugin/lib/rowsCache.js`：单仓 **12 万行 / 32MB**；新增 **56MB 总预算**，写完后按仓数与总字节
  LRU 淘汰；条目多存一个 `pool`。
- `plugin/lib/client.js`：`ROW` + 7 个访问器；`take()` 解析出数组直接入行（不再建对象）；
  `foldIssues` / 筛选 / 渲染 / `mergeTimelineRows` / 高度键全走访问器；客户端缓存同样 12 万 / 32MB / 56MB；
  请求带 `&format=2`；空标签共用 `NO_TAGS`，折叠不再每行造数组。
- 测试：`run.mjs` **82**（新增格式门、总预算两条），`render.mjs` **58**（fixture 换成数组）。

### 2. 实测（10 万行，`probe-format.mjs`）

| 形状 | 常驻 | 线上 | 宿主重发 | 客户端收行 |
| --- | --- | --- | --- | --- |
| 现状：7 槽数组 + 驻留 | 356B/行（33.9MB） | **23.6MB** | **55ms** | **43ms** |
| 同上但不驻留 | 451B/行（43.0MB） | 23.6MB | 55ms | 43ms |
| 旧对象形状（对照） | 364B/行（34.7MB） | 32.1MB | 77ms | 72ms |

fold 在数组输入上 **203B/行**（100k 约 19.3MB、33ms）；本仓 173 行的行常驻 510B/行（`probe-memory`）。

### 3. 与假设的差异

- **没做自适应**（`os.totalmem()` / `navigator.deviceMemory`）。固定默认值已经把最坏情况钉在
  56MB/端：两个 10 万行仓约 47MB 线上（G2 口径），加机器探测是多一条分支、少一条可测路径；
  “默认够用”就不需要自适应。
- **总预算从 128MB 收到 56MB**：按实测 23.6MB/10 万行，56MB 覆盖两个大仓（47MB）并给标题更长的仓
  留约 18% 余量；128MB 找不到对应场景。单仓上限仍是 32MB，够 12 万行。
- 行的线上格式变了（`format=2`），这是本 issue 之外的**协议变更**，已在 README 写明。

### 4. 验收对照

- 100k fixture：线上 23.6MB、重发 55ms、常驻 34MB——都在提案内；
- 本仓（173 行）：82 + 58 用例全过，行为不变；
- 旧客户端：新增用例覆盖 400 与刷新提示；
- 增量 / delta：boundary 改读下标，原有 9 条阶段 3 用例全过；
- 总预算：宿主与客户端各一条淘汰用例（56MB 下两份 30MB 只留最近一份）。

### 5. 已知边界

- **旧标签页要刷新**：不刷新会拿到 400（这是刻意的，比静默空列表好）。
- **fold 仍复制一份**（203B/行）：客户端总占用 ≈ 行 + fold；要再省得做 fold 增量/懒折叠，另开。
- 100k 仓首次仍要 ~0.3s 与一次 24MB 传输；之后 HEAD 未变 0 字节。
- 真机验证（宿主重启后的 `x-kiln-mode` / `format=2`）仍需重启 DSH 做一次。

## 追加（2026-10-30）：总预算 56MB → 64MB

- 取整：**64MB = 单仓 32MB × 2 个仓**，正好是默认配置的上界，不用再记一个零碎的数。
- 含义变化：默认配置下总预算恰好等于乘积，**不会触发淘汰**；它防的是以后放宽仓数或单仓上限时
  乘积一路涨上去，属于兜底而不是常用路径。
- 测试同步：客户端那条改为“预置一份 40MB + 再记一份 30MB”——两仓单看都合法，总和 70MB > 64MB，
  才会挤掉旧的那份；宿主那条仍用可注入的小额度验证同一段逻辑。
- 其余不变：单仓 12 万行 / 32MB、无用户配置、两端同一口径。
