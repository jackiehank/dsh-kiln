# 聚焦态的关系清单，归 issue 页还是关系页

## 背景

三页共享一个焦点 issue，是 `kiln-views-shared-focus` 定下的。当时给关系页配了两种取景——
「图」看形状、「列表」读文字——理由是：图上只能看出“有关系、什么类型靠线型”，关系名、方向、
母/子这类结构用文字读更快。图那半后来一路改到线型阶梯 + 图例（`kiln-graph-label-threshold`），
列表那半基本停在第一版。

用下来暴露两个问题：

1. **同一份“焦点邻居”有两个文本出口**：issue 页有焦点时本来就只剩焦点 + 一跳邻居（`scopedIssues`），
   关系页列表的聚焦态又是这同一批 issue 的分组版。两页都在讲“焦点周围有什么”，只是分组粒度不同。
2. **关系页的“列表”与它的“图”是两种取景，但只有列表会讲关系名**，于是这个页签一半在图上一半在表里，
   页内分段切换的意义被稀释：想看结构得切图，想看名字得切列表。

倾向的改法：**把关系页列表的聚焦态搬到 issue 页，关系页去掉「列表」，只留「图」。** 这样
“关系页 = 看形状”“issue 页 = 读结构”，一页一件事。

## 现状（代码位置）

- 关系页两种取景：`plugin/lib/client.js:58`（`RELATION_MODES`），切换在 `RelationPanel`
  （`plugin/lib/client.js:1170`）；工具栏还挂着布局方向 / 视图（全局·聚焦）/ 跳数三个分段。
- 列表的**无焦点**态：全局边表，按词表分组（`globalRelationRows`，`:437`）。
- 列表的**聚焦**态（要搬走的那块，`RelationList`，`:1221`–`:1349`）：
  - 焦点行（`focus: true`）；
  - `↑ part-of: <母>` 面包屑，点它换焦点；
  - 子 issue 组：超过 4 个折叠成「展开全部 N」；
  - 强关系组：`blocks` / `caused-by` / `supersedes`，行内带 `→ / ←` 与关系名；
  - 弱关联：默认折叠成「+N 弱关联 · relates-to」按钮。
- issue 页（`IssuePanel`，`:935`）：有焦点时 `scopedIssues` 已经过滤到焦点 + 一跳邻居，
  `sortIssues` 把焦点行钉在第一条（`:692`）；但**不分组、不标关系名**，和没焦点时长得一样。
- 时间线在焦点时同样收窄（`scoped`）——这次不动它。

## 目标

1. 关系页只留图：去掉「图 / 列表」分段与列表代码路径。
2. issue 页承担“聚焦态”：有焦点时读出**结构**（母 / 子 / 阻塞 / 因果 / 取代 / 弱关联），
   每行带关系名与方向；没焦点时维持现在的全量列表。
3. 焦点仍是**一份**跨页状态，不新增第二份；新增的页内状态仍只存内存（不落盘）。

## 边界

- 不改关系图本身（线型、图例、淡化、布局都不动）。
- 不新增“有向 / 无向”开关；能不加旋钮就不加（沿用“有名字的视图”这个取向）。
- 不做持久化（刷新即清空），不进 URL。
- 关系页去掉列表后，**全局边表的文本读法消失**：全局只能靠线型 + 图例认关系。
  这是这次改动的明确代价，记在这里而不是装作没有。

## 验收

- 关系页没有「图 / 列表」分段；内存里残留的 `relationMode` 不会让视图报错。
- issue 页有焦点时：能看到焦点行、母 issue 入口、子 issue、强关系分组（带 `→ / ←` 与关系名）、
  弱关联入口；行仍可点开动作、`f` 仍能换焦点。
- issue 页无焦点时与今天一致（全量、最近动作排序、可展开）。
- `npm test --prefix plugin` 通过（现有 28 + 25 例，按改动增删）。

## collect：聚焦态到底有多少行可读

口径：`kiln graph --json` 取两个仓库的边（本仓 9 条、`~/kiln` 73 条），
按 `relatedOf`（`plugin/lib/client.js:392`）的规则折叠成 母 / 子 / `blocks` / `caused-by` /
`supersedes` / `relates-to` 六组。“默认行数”按**今天列表的默认形态**数：焦点 1 行 + 母 1 行 +
子（最多 4 行，多的折成一个按钮）+ 强关系行，弱关联不展开。

| | 本仓（9 issue / 9 边） | `~/kiln`（58 issue / 73 边） |
| --- | --- | --- |
| 邻居总数 | 中位 2，最大 3 | 中位 2，p90 5，最大 9 |
| 其中强关系 | 中位 1，最大 2 | 中位 **0**，p90 2，最大 5 |
| 其中弱关联 | 中位 1，最大 3 | 中位 1，p90 4，最大 8 |
| 一条关系都没有 | 1 / 9 | 6 / 58 |
| 只有弱关联 | 1 / 9 | 26 / 58 |
| **焦点态默认行数** | 中位 2，最大 3 | **中位 1**，p90 3，最大 6 |

`~/kiln` 的默认行数直方图（行数 → 有多少个焦点）：`1 → 32`、`2 → 18`、`3 → 5`、`4 → 1`、
`5 → 1`、`6 → 1`。最忙的焦点是 `cli-necessity`（9 个邻居）、`help-relation-flags`（9）、
`relation-rendering`（8）。

结论（交给 hypothesize）：

1. **弱关联默认折叠时，55%（32 / 58）的焦点页只剩焦点自己一行**——26 个“只有弱关联”加 6 个
   “没有任何关系”。关系页列表今天就是这个形态，但它藏在“列表”分段里，不必天天面对；搬到 issue 页、
   变成主视图之后，这个空荡会被放大。要么弱关联默认展开（最多 9 行，仍可控），要么让焦点行自己
   带内容（展开它的动作）。
2. **长尾很浅**：最大 9 行、p90 = 5。这一页不需要虚拟列表，也不需要激进折叠，把“一到九行都好看”
   做出来就够了。
3. **本仓不适合做观感判断**：9 条边、最大 3 行，看不出问题；判断要按 `~/kiln` 的量级来。

## hypothesize：聚焦态的三种形态

先把三个方案共用的部分定下来，再比差异：

- 关系页只剩图（`全局 / 聚焦 + 方向 + 跳数` 三个分段保留）；
- 关系名与方向只在 issue 页的聚焦态里以文字读出（就是今天列表聚焦态的行内 `→ blocks`）；
- 焦点行可以点开动作、可以 `f` 换焦点——与今天的 issue 行一致。

三个方案的差别只有一件事：**聚焦之后，还能不能在同一页看到无关的 issue。**

### A. 焦点即切换，只留一条文字链（推荐）

无焦点 = 今天的全量列表；有焦点 = 搬来的分组邻域，页首一行
`焦点：x · 3 个邻居 · 查看全部 issue`，点“查看全部 issue”回到全量列表（焦点仍保留，焦点行钉第一，
即今天 `sortIssues` 的行为）。

| | |
| --- | --- |
| 好处 | 不加控件；“有焦点就看结构”是个自然默认；需要的逃生口只是一条文字链，成本远低于一排按钮 |
| 代价 | 页内多一个布尔状态（邻域 / 全量），两种形态长得像，得靠页首那行字区分 |
| 风险 | “聚焦后找不到别的 issue”要靠那行文字提示，发现性一般 |

### B. issue 页也做 `全部 / 聚焦` 分段，与关系页对称

工具栏一行 `[全部 | 聚焦]`，设焦点时自动切到聚焦档。

| | |
| --- | --- |
| 好处 | 对称、看得见、随时跳回全量；跟关系页的 `全局 / 聚焦` 一眼能对上 |
| 代价 | issue 页凭空多一排按钮；两个页签各有一对“全局/聚焦”，其实一个管图一个管列表，容易以为它们联动 |
| 风险 | 三个分段的工具栏已经出现在关系页，再来一排会有“面板比内容重”的观感 |

### C. 焦点卡片 + 全量列表都留着

issue 页始终全量；有焦点时在列表上方插一张“焦点卡片”（母 / 子 / 强关系 / 弱关联），
邻居行在列表里加标记。

| | |
| --- | --- |
| 好处 | 上下文不丢；就算焦点没有邻居，下面也总有全量列表，不会空 |
| 代价 | 同一批 issue 出现两次（卡片一次、列表一次）；卡片最多 9 行再加上全量列表，页面长度翻倍 |
| 风险 | 与“一页一件事”相反，等于把关系页的列表和 issue 页的列表并排放在同一屏 |

### 选 A 的理由

1. 三页共享焦点，“聚焦”本身就是一个模式。再给 issue 页一对显式的 `全部/聚焦` 分段，等于把同一个
   概念讲两遍——关系页那对管的是**图**，issue 页这对管的是**列表**，联动关系说不清就是坑。
2. collect 说“页面太空”的根因是**内容太少，不是入口太少**：55% 的焦点只有一行。补内容的两件事
   （弱关联默认展开、焦点行动作默认展开）都跟方案无关，先做它们，A 就足够了。
3. 真正需要“聚焦后读全量”的时刻，今天也能做到（`×` / Esc 退出聚焦）；A 只是把这条退路顺手
   画在页首，代价一条文字链。

### 方案无关、但必须一起做的三件事

1. **弱关联默认展开**：`relates-to` 不再折成 `+N 弱关联` 按钮。collect 的直方图说明不这么做，
   一半以上的焦点页只有一行。
2. **焦点行默认展开它的动作**：issue 页的价值是“读”，焦点自己没有邻居时，至少能读它的历史。
   建议用 issue 页独立的展开状态（默认开），不要复用三页共享的 `expanded`——否则 timeline 会被
   顺带展开，切页手感突变。
3. **关系页删干净**：`RELATION_MODES`、`relationMode` 的内存字段、列表分支、只服务于它的
   `globalRelationRows` 一并去掉；旧内存里残留的 `relationMode` 必须被忽略而不是报错。

### 落地顺序（实际执行）

1. 关系页删列表：分段、状态、列表分支；工具栏只留方向 / 视图 / 跳数。
2. 抽 `IssueFocusList`（从 `RelationList` 的焦点分支搬）：母 crumb、子组、强关系组、弱关联默认展开。
3. issue 页：有焦点渲染 `IssueFocusList`，无焦点渲染今天的 `IssuePanel`；退出聚焦只走头部 `焦点：x ×`
   （讨论后决定不加页内链接）。
4. 测试：`plugin/test/render.mjs` 里关系页列表相关的用例迁到 issue 页，删掉关系页分段的断言。
   `run.mjs` 没加“旧 `relationMode`”用例——那个字段只从内存读一次、读到也没人用，
   删掉 `EMPTY_VIEW_STATE` 里的定义后不会抛错，写用例反而是给不存在的路径加保护。
5. 观感核对按 `~/kiln` 的量级走（58 issue / 73 边），必须重启桌面应用才能看到新代码。

## 落地（apply）：关系页只剩图，聚焦态归 issue 页

**定案（讨论结论）：A，但不要页内那条文字链。** 退出聚焦就走头部已有的 `焦点：x ×`（和关系页
一样，`Esc` 也行）——聚焦是一个跨页状态，出口只该有一个，页内再来一条“查看全部 issue”是第二种说法。

弱关联按 collect 的结论**默认展开、不给收起开关**；焦点行动作**默认展开**（独立状态 `focusOpen`，
换焦点时重置为开）。

代码（`plugin/lib/client.js`）：

- 关系页：`RelationPanel` 只渲染三个分段（方向 / 视图 / 半径）加 `GraphPanel`。删掉
  `RELATION_MODES`、`relationMode` 状态与内存字段、`RelationList`、`globalRelationRows`，
  以及只服务于全局边表的 `.dkf-grow` / `.dkf-endpoint` 两条样式。
- issue 页：有焦点渲染新的 `IssueFocusList`（母 crumb / 子组（>4 折叠）/ `blocks` / `caused-by` /
  `supersedes` / 弱关联），行内仍带 `→ ←` 与关系名；无焦点还是 `IssuePanel` 的全量列表。
- 焦点行用独立的 `focusOpen`，没有复用三页共享的 `expanded`——否则在 timeline 里展开同一条 issue
  会连带改掉 issue 页的手感。

测试：`npm test --prefix plugin` → 28（宿主）+ 26（渲染）。改动是把关系页列表的两例迁成 issue 页
结构断言（分组表头、行内方向、弱关联默认展开、焦点行默认展开/可收起），再补一例“issue 页不画图”。

**代价（当时确认过，这里记着）**：全局边表的文本读法没有了。没有焦点时，关系只能从图上读线型、
配合图例；要看“A ← caused-by B”这种句子，得先把焦点落到 A 或 B。

## 待定（下一轮讨论）

1. 时间线在焦点时同样收窄，这次没动——要不要也做成“结构优先”，等 issue 页用一阵再说。
2. 焦点为空的 issue（没有任何关系，`~/kiln` 有 6 个）现在只剩焦点行 + 它的动作；是否补一句
   “这个 issue 还没有关系”。
3. 聚焦态下节点标签与边标签（`kiln-graph-label-threshold` deferred 的两项）仍未动。
