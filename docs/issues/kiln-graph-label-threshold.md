# 标签门槛：边标签按需出现，节点标签分级

## 背景

关系图现在把两类文字**永远全显示**：

| 类型 | 是什么 | 现状 |
| --- | --- | --- |
| **边标签** | 关系类型（`caused-by` / `blocks` / `relates-to`） | 每条边都写一遍，`caused-by` 在 `~/kiln` 里要重复 19 次 |
| **节点标签** | issue id（`kiln-views-shared-focus` 这类 20+ 字符） | 决定节点宽度，进而决定整张图的横向尺寸 |

已经量过的两个数（`kiln-graph-readability` 的 collect）：

- 只去掉**边标签**：画布就小 12%、交叉少 14%（4538×2018 → 3995×1680，112 → 98）；
- 节点标签影响更大：Pele 用文字宽度量节点，标签长 → 节点宽 → 图更宽。

## 目标

在**不丢信息**的前提下把这两块噪声降下去：

1. 边标签：默认不显示，**聚焦时显示焦点那一圈**、**hover 单条边时显示那一条**；
2. 节点标签：始终看得见，但**小比例时截断**（放大后恢复全名）。

“不丢信息”指：任意时刻都能知道某条边是什么关系（靠 hover / 聚焦 / 线型），
以及某个节点是哪个 issue（靠列表视图或放大）。

## 两类标签为什么不能一视同仁

- **边标签**可以“按需出现”：关系类型已经部分编码在线型里（实线 `part-of`/`blocks`、
  虚线 `caused-by`/`supersedes`、无箭头线 `relates-to`），且列表视图保留完整关系名；
- **节点标签**不能整体隐藏：藏了就不知道是哪个 issue。它的问题不是“显不显示”，是“多长”。

## 方案草案

| 部分 | 做法 | 代价 |
| --- | --- | --- |
| 边标签 | 渲染后统一加 `dkf-elabel-hidden`，聚焦/hover 时按 `data-id` 摘下来（与边淡化同一套 id 配对，见 `kiln-graph-edge-dim`） | 纯 class，不重排 |
| 节点标签截断 | 生成 mermaid 时就截断（如 12 字符 + `…`），节点因此变窄 | **会重排**，所以只能按“档位”切换，不能跟着缩放实时做 |
| 档位触发 | 读 Pele zoom 的 `scale`（`handle.zoom.scale`），跨过阈值时切一次档（带防抖） | 需要监听 wheel / 双指 / 按钮，Pele 没有“缩放变化”事件 |

**分两版做**：

- 第一版（便宜、无风险）：只做**边标签按需** + **hover 显出标签**，纯 CSS class，不动布局；
- 第二版（要看收益再决定）：节点标签分级截断，按缩放档位重生成文本。

## 边界

- 不改数据面（仍是同一份快照）；
- 边标签的显隐是纯视觉，**不重排**；
- 节点标签截断会重排，所以只在**跨档**时发生，且不打断当前视图（缩放中不重画）；
- 「聚焦」视图与「全局」视图共用同一套规则。

## 验收

1. 全局视图默认看不到边标签，图明显变干净；
2. hover 某条边：那一条的标签出现（线、箭头、标签同一条边，靠 `data-id` 对齐）；
3. 聚焦某 issue：它那一圈的边标签出现，其余仍隐藏；
4. 切焦点不重排（沿用全局视图的既有验收）；
5. 节点标签截断（若做第二版）在放大后恢复全名，且列表视图始终是全名。

## 待定

1. 边标签默认隐藏会不会让人看不懂图？要不要“首次进入时全部显示 2 秒再收起来”之类的过渡；
2. 节点标签截断的规则：截前 12 字符、还是只留最后一段（`…-shared-focus`）；
3. 档位阈值定在哪（当前是先看 0.7 / 1.0 两个点）；
4. hover 在触屏上不可用，是否退化为“点选边”。

## collect：Pele 的边能调什么

用仓库里 vendored 的 `client.pele.js` 逐项试（`render()` 不需要浏览器），结论按“能改什么”归类：

### 1. 内置 mermaid 语法（写文本时就能定）

| 写法 | 渲染结果 |
| --- | --- |
| `a --> b` | `<path>` 无额外属性，取父级的 `stroke="var(--_l)"` |
| `a -.-> b` | 同上（Pele 把虚线也画成实线路径，线型由 mermaid 语义决定） |
| `a ===> b` | path 上直接带 `stroke-width="2.5"` |
| `a --- b` | 无箭头（没有 `.pele-marker`） |

### 2. `linkStyle <序号> …`：**可用**，而且能改颜色

```mermaid
linkStyle 1 stroke:#00aa00,stroke-width:3px
```

渲染成边组上的内联样式：

```html
<g class="pele-edge" data-id="L_n_b_n_c_0" style="stroke:#00aa00;stroke-width:3px;">
```

三个要点：

- **序号 = 文本里边的声明顺序**（第 0 条、第 1 条…），实测对得上；
- **箭头会自动跟随**：设了 `stroke:#ff0000` 之后，`.pele-marker` 的 `fill` 也变成 `#ff0000`；
- `display:none` 这类非描边属性**不生效**（被忽略，边照画）——想隐藏要自己用 CSS。

### 3. CSS：可以在渲染后按类 / 按 `data-id` 调

| 选择器 | 控制什么 |
| --- | --- |
| `.pele-edges` | 所有边的父组（`stroke`、`fill:none` 在这层） |
| `.pele-edge[data-id]` | 单条边（线 + 箭头） |
| `.pele-edge-label[data-id]` | 单条边的标签（**与边同 id 的兄弟节点**） |
| `.pele-marker` | 箭头（`fill`） |
| `--pele-line` | 全体边的默认色（主题变量） |

### 4. 几个坑

1. **平行边的 `data-id` 序号不连续**：同一对起止的两条边是 `L_n_a_n_b_0` 与 `L_n_a_n_b_2`（不是 0、1）。
   所以 `data-id` 只适合**前缀匹配**（我们已经在用），别去猜序号；
2. `linkStyle` 的序号与 `data-id` 的序号**不是同一套**，别混用；
3. `config.flowchart.curve`（basis/linear/stepBefore）在这张小图上**看不出差异**，路径 `d` 相同——
   想改曲线形状大概得靠 CSS `stroke-linejoin`（只影响拐角），Pele 不暴露曲线类型；
4. 箭头颜色跟着线的 `stroke` 走，但**不跟随 `stroke-dasharray`**；虚线的箭头仍是实心三角。

### 对本 issue 的直接用处

- **藏边标签**：`.pele-edge-label{display:none}` 或按 `data-id` 摘除——纯视觉，不重排，正是第一版要的；
- **强调某条边**：不必用 `linkStyle` 重生成文本，CSS 直接改 `stroke` / `stroke-width` 就行（也和边淡化同一套 id 配对）；
- **hover 单独显示**：`.pele-edge-label[data-id="…"]` 精确到条，靠 `data-id` 配对即可，无需重画。

## collect：几套“成套”的关系语汇，以及我们这五类怎么排

用户问的是：关系图里这几类关系，有没有成体系的设计可以参考。找了四套成熟语汇 + 一套理论。

### 1. UML 六种关系（最成熟的“线型 + 端饰”体系）

| 关系 | 线 | 箭头端 | 语义 |
| --- | --- | --- | --- |
| 依赖 Dependency | 虚线 | 普通箭头 | 用到、但不持有 |
| 关联 Association | 实线 | 可无、可箭头 | 长期联系 |
| 聚合 Aggregation | 实线 | **空心菱形**（指向整体） | 整体-部分，可独立 |
| 组合 Composition | 实线 | **实心菱形**（指向整体） | 整体-部分，同生共死 |
| 泛化 Generalization | 实线 | **空心三角**（指向父） | is-a |
| 实现 Realization | 虚线 | **空心三角** | 接口实现 |

要点：它把**线型（实/虚）**与**端饰（箭头/菱形/三角）**当成两个正交变量，六种关系靠这两个变量的组合区分。

### 2. SysML 需求图

`derive` / `satisfy` / `verify` / `refine` / `trace` / `copy`——一整套围着他“需求如何被论证”的关系，
做法是**线型 + 关键字标签**（标签写在线上），而不是靠端饰。适合“关系种类多、但视觉区分可以靠文字”的场景。

### 3. 因果图（DAG）的约定

单头箭头 = 因果方向；**实线 = 已测量，虚线 = 推断/未测量**。
这套约定把“这条因果有多可信”编码进线型，正好对应我们 `caused-by` 的解释性地位。

### 4. Jira 的链接类型（与我们最像的一套）

`blocks / is blocked by`（强依赖、有顺序）、`relates to`（松散相关、无顺序）、`clones / duplicates`（替代/重复）、
`causes`（因果）。它的分类维度其实就是我们词表里的两个槽：
**ordering（blocks/part-of）与 lineage（causes/supersedes/relates-to）**。

### 5. Neo4j Bloom 的图例面板

按**关系类型**分配颜色、大小、标题属性，并维护一份图例——适合“关系种类由用户定义”的产品。

### 6. 理论：Bertin 的视觉变量

位置、大小、形状、纹理（实/虚/点）、方向、色相、明度。
**一套好设计的标志是每个变量只承担一个维度**——否则同一个变化会被读成两种意思。

## 我们能画的（实测，接着上一节）

| 想表达 | mermaid 写法 | Pele 渲染 | 可用性 |
| --- | --- | --- | --- |
| 方向 | `-->` / `<-->` | 箭头 1 个 / 2 个 | ✅ |
| 粗线 | `===>` | path 带 `stroke-width="2.5"` | ✅ |
| 虚线 | `-.->` | 与实线同一路径，线型由 mermaid 语义保证 | ✅ |
| 叉头（“作废/否定”） | `--x` | 两个交叉笔画 | ✅ |
| 菱形 / 圆形端饰 | `--o` | **不渲染任何标记** | ❌ |
| 空心三角 | 无语法 | — | ❌ |

也就是说 **UML 的菱形/三角端饰这套用不了**，能用的词汇是：箭头有无/数量、叉头、实线/虚线、粗细、颜色。

## 一个成套提案（五类关系）

变量分工，每个变量只说一件事：

| 变量 | 承担 | 不承担 |
| --- | --- | --- |
| **线型**（实/虚） | 约束力：结构性与强制（实） vs 解释性与历史（虚） | 不表达方向 |
| **端饰**（箭头/叉头/无） | 方向性和“作废” | 不表达强弱 |
| **标签**（默认隐藏） | 具体关系名 | 不参与扫读 |
| **颜色** | **不用**——节点已经用动作色编码，边再用颜色会撞 | — |

| 关系 | 线 | 端饰 | 借自 |
| --- | --- | --- | --- |
| `part-of` | 实线 | 箭头指向整体 | UML 聚合 + Jira 子任务 |
| `blocks` | 实线（可加粗） | 箭头指向被阻塞者 | UML 依赖 + Jira blocks |
| `caused-by` | 虚线 | 箭头 | 因果图（虚线=推断性） |
| `supersedes` | 虚线 | **叉头**（作废） | 因果图虚线 + “x = 否定”的通用记号 |
| `relates-to` | 实线 | **无箭头** | UML 关联 / Jira relates to |

与现状的差别只有一处：**`supersedes` 现在和 `caused-by` 长得一样（都虚线+箭头）**，
按这套应该换成叉头——这也正好回答“同一张图里两种关系形状完全相同”这个隐患。

## collect：用「线条样式」区分关系类型

### 为什么不用端点标识

用户提出的问题很实在：如果一个 issue 既是好几个 issue 的整体、又被另一个 issue 取代，
那指向它的线会很多，**端点处的标识（菱形/三角/叉头）会叠在同一个入口**，谁也认不出来：

![端点标识在汇合处叠在一起，而线型不会](assets/edge-markers-vs-linestyle.png)

线型没有这个问题：形状沿整条线重复，不占用端点。

### 别人怎么用线型（不是端点）

| 体系 | 线型承担什么 |
| --- | --- |
| **BPMN** | 顺序流实线、消息流**点线**、关联**点线**——跨池与同池靠线型分 |
| **UML** | 依赖/实现 = **虚线**；关联/泛化 = 实线（UML 1.5 的对象流也是虚线，2.0 改成实线，因为光靠线型不够——需要一个对象端） |
| **DMN 决策图** | 信息需求 = 实线箭头；知识需求 = **虚线** |
| **因果图** | 实线 = 已测量、**虚线** = 推断 |
| **uDraw(Graph) / MATLAB** | 把线型当成一级属性：`single/double` × `solid/dotted/dashed`，以及 `-, --, :, -.` |

共性：**线型编码的是“这类关系有多硬”**（强制/推断、同层/跨层），端点标识编码的是“端点扮演什么角色”（整体、接口、否定）。
我们的问题是前者（五类关系的强弱与方向），所以该落在线型上。

### Pele 能不能画（实测）

`linkStyle` 可以写任意 `stroke-dasharray`，实测这几种都被原样输出：

| 写法 | 渲染结果 |
| --- | --- |
| `stroke-width:2px` | 内联到边组 |
| `stroke-dasharray:10 4` | 长虚线 |
| `stroke-dasharray:4 3` | 短虚线 |
| `stroke-dasharray:1 4, stroke-linecap:round` | 点线（圆头） |
| `stroke-dasharray:10 3 2 3` | 点划线 |

也就是说**线型完全由我们在生成文本时决定**，不需要端点标识、不需要额外 CSS，也不会与边的淡化/隐藏冲突。

### 一个阶梯式提案

把五类关系按「墨量」排成一个阶梯——结构性越强，线越实越粗：

![五类关系的线型阶梯](assets/edge-line-styles.png)

| 关系 | dasharray | 线宽 | 箭头 |
| --- | --- | --- | --- |
| `part-of` | 实线 | 2.6 | 有 |
| `blocks` | 实线 | 1.5 | 有 |
| `caused-by` | `10 5` | 1.5 | 有 |
| `supersedes` | `9 3 2 3`（点划） | 1.5 | 有 |
| `relates-to` | `2 5`（点线） | 1.3 | **无** |

同一张图上的效果：

![五类关系同框](assets/edge-relations-applied.png)

两条设计理由：

1. **只有一个变量在动**：线型的密度沿“约束力”单调递减（ordering 实线 → lineage 虚线 → 无向点线），
   不引入第二套编码（颜色留给节点的动作色）；
2. **同一槽内再加一档**：`part-of` 用粗实线、`blocks` 用常规实线；`caused-by` 长虚、`supersedes` 点划——
   这样连“同一槽里谁更强”也能看出来。

### 代价

- 点划线在**缩放很小**时可能糊成一片（1.5px 线宽下，虚线间隔小于 1 个屏幕像素）；
  真要细调，可以在窄屏/小比例时退化为“实线 + 点线”两档；
- 五类里 `part-of` 与 `supersedes` 在 `~/kiln` 一次都没出现（见上一张表），
  所以这套阶梯当前的“实际可用性”主要是前三类；
- `linkStyle` 按**声明顺序**生效，所以生成文本时必须能稳定复现边的顺序（我们现在就是有序的）。

> 也不会因为移动文档目录而失效。

## 落地（apply）：线型阶梯 + 图例

按上一节的阶梯实装，**没有引入端点标识**：

| 关系 | linkStyle | 箭头 |
| --- | --- | --- |
| `part-of` | `stroke-width:2.6px` | 有 |
| `blocks` | `stroke-width:1.6px` | 有 |
| `caused-by` | `stroke-width:1.6px,stroke-dasharray:10 5` | 有 |
| `supersedes` | `stroke-width:1.6px,stroke-dasharray:9 3 2 3` | 有 |
| `relates-to` | `stroke-width:1.3px,stroke-dasharray:2 5` | 无 |

做法：生成 mermaid 时，**每条边后面紧跟一条 `linkStyle <序号>`**（序号 = 边的声明顺序，稳定）。
文本里所有有向边统一写 `-->`，线型完全由 `linkStyle` 决定——这样虚线与实线不必依赖 mermaid 的
`-.->` 语法，也能精确控制 dasharray 与线宽。

**图例**：图下方一行五条样条，用与图上**同一份** `EDGE_STROKE` 生成（同一个解析函数，
不存在“图例和实际画的不一样”）；当前视图没画出来的那几类自动淡出（例如全局视图里 `relates-to`
是淡的，因为无向关系只在「聚焦」里出现）。

验证：

- `plugin/test/render.mjs` **25 例**：新增图例行数 / 名称顺序 / 未画类淡出 / 样条的
  `strokeWidth` 与 `strokeDasharray` 逐条比对；
- 真数据：`~/kiln` 26 节点 / 20 条边全部带上样式，画布仍是 **2578×468**——
  线型只改外观，不影响布局。

## 落地（apply）：去掉边标签

关系类型现在由**线型 + 图例**承担，边上一律不再写 `|caused-by|` 这类文字——
一条 `caused-by` 出现二十次，本来也读不出额外信息。

- 文本层直接去掉标签（不是 CSS 隐藏），因此 dagre 不再为边标签预留空间：
  `~/kiln` 的全局视图从 **2578×468 → 2578×372**（高度 −21%），
  SVG 里 `.pele-edge-label` 元素数量为 **0**；
- `buildMermaid` 顺带返回 `drawn`（这次真正画了哪些关系类型），图例直接用它判断“哪类没画”，
  不再靠正则从文本里猜；
- 代价要记住：标签不在 DOM 里了，**以后要做“hover 显示那一条边的关系名”就得重新生成文本**
  （或者改成“文本保留 + CSS 隐藏”的路线，那时再把标签加回来）。

验证：`plugin/test/render.mjs` 25 例，其中一条直接断言**边行里不再出现 `|`**；
真数据渲染 0 个 label 元素、高度 −96px。

## 落地（apply）：图例重做，并把因果箭头改成「因 → 果」

第一版图例太“技术味”：`part-of / 属于谁 · 实线粗`——三个信息挤在一行，既没说明谁指向谁，也没画出箭头。
按用户意见重做：

- **一条一句人话**：`A 是 B 的一部分` / `A 阻塞 B` / `A 引发 B` / `A 取代 B` / `A 与 B 相关`；
- **样条带箭头**：有向的四类画出箭头，`relates-to` 不画（它就是无向的）；
- **不再写线型名**（“实线粗”“长虚”这些删掉）——线型本身就是给人看的，不需要再用文字解释一遍；
- 排版改成两列自适应网格，当前视图没画的关系整行淡出。
