# kiln-list-window — 列表先渲染 100 行、滚到底再要下一批，为规模增长预留空间

- **domain**：integration
- **关联**：part-of `kiln-many-issues`（伞 issue，负责上游缺口与 100k 方向）；relates-to `kiln-session-cache`（Tier 0 已做，本次是 Tier 1 的窗口部分）

## 问题

时间线与 issue 列表现在都是**全量渲染**：

- 时间线一行一个动作，10 万动作 ≈ 10 万行、约 70 万 DOM 节点；
- issue 列表一行一个 issue，但行内色条是「每个动作一个块」，DOM ≈ `issue 数 × (10 + 平均动作数)`；
- 流式期间每 50ms 发布一批，整体列表重渲染。

当前真仓（24 / 84 issue、153 / 455 动作）完全没有压力，但下一次规模跳变（1k+ 动作）时，
首屏与滚动会先于取数变成瓶颈。先做一层**渲染窗口**：只挂前 W 行，滚到底再追加一批——
不改变数据（动作流仍然全量读），只给 DOM 一个上界，为后续虚拟化/上游分页留出位置。

## 规模预估（本次实现的取舍依据）

| 规模（动作 / issue） | 时间线行 | issue 行 + 色条块 | 建议 |
| --- | --- | --- | --- |
| 455 / 84（当前） | 455 | 84 + 153 | 不需要特殊处理 |
| ~2k / ~300 | 2k | 300 + 2k | `content-visibility` + 色条 cap 即可 |
| ~5k / ~1k | 5k | 1k + 5k | **窗口 W=100–200 + 滚动加载**（本次） |
| ~10k / ~2k | 10k | 2k + 10k | 需要虚拟化；此时流约 4MB |
| 50k+ | 50k | 5k + 50k | 上游分页优先（流 20MB+），窗口/虚拟化只能缓解 |

判定信号：**首帧 > 150ms 或滚动掉帧 > 5%** 就该继续往下走；窗口是 2k–5k 区间的最低成本方案。
（数字是结构推算，尚未在浏览器里量；合成仓探针留给 `kiln-many-issues`。）

## 做什么

- 时间线、issue 列表、搜索结果都按 **W = 100** 行渲染，底部给「已显示 X / N · 继续滚动自动加载…」；
- 接近底部（320px）自动追加 100 行，不需要点按钮；
- 窗口只在**当前列表**内生效：切页、换焦点、改筛选、改搜索词、换仓库、刷新都重置回 100；
- 页头计数仍是总数，底部显示“已显示”，两者不混；
- 列表不足 100 行时行为与现在完全一致（没有 footer）。

## 非目标

- 不做虚拟化（只挂可视区）；不做数据层分页（上游没有 limit/offset）；
- 不改取数（动作流仍是全量流）；不为窗口加持久化；
- 不做合成仓探针（留给 `kiln-many-issues`）。

## 验收

- 250 行 fixture：首次只渲染 100 行，footer 显示「100 / 250」；预设窗口 200 时显示 200、无 footer；
- 滚到接近底部只追加 100 行，不一次全出；
- 切页 / 筛选 / 搜索词变化后窗口回到 100，滚动位置回顶；
- 现有 55 宿主 + 53 渲染用例全绿，新增窗口用例覆盖“截断 / 追加 / 重置”；
- issue 列表不足 100 条时行为不变（本仓 24、`~/kiln` 84）；时间线在本仓（157 动作）与
  `~/kiln`（455 动作）都会先挂 100 行并显示「已显示 X / N」，这是本次有意引入的变化。

### 验证

- 宿主 **55**、渲染 **57** 用例全绿；`node --check` 覆盖 6 个文件。
- 窗口用例断言：首屏行数 = 100、页头计数 = 总数、footer 文案「已显示 100 / N」+「继续滚动自动加载…」、
  没有手动按钮；窗口覆盖全部时 `.dkf-more` 不出现。
- 真仓：issue 列表 24 / 84 条都不足 100，行为不变；时间线本仓 157、`~/kiln` 455 条会先挂 100 条
  （footer 显示 100 / 157、100 / 455），滚到接近底部自动追加 100。
- 搜索跳转：目标动作还没挂出来时，滚动 effect 会一批一批追加窗口再滚过去；追加到总数仍没有
  就放弃（不无限循环）。切页的窗口重置放在 `selectTab` 里，避免把跳转刚追加的窗口抢回第一屏。

### 代价与边界

- 被窗口挡住的行**不在 DOM 里**：浏览器 find-in-page 搜不到，直到滚到那一批；这是窗口与
  虚拟化共同的产品代价，换来 DOM 上界。
- 键盘 roving 焦点只能在已挂载的行之间移动；继续加载靠滚动触发的 sentinel（无按钮）。
- 窗口只是渲染层：动作流仍全量读，100k 动作的网络/解析成本不变（`kiln-many-issues`）。
- 阈值（100 行 / 320px / 每批 100）是本次的默认值，等浏览器实测（首帧 >150ms 或掉帧 >5%）
  再决定是否调大或升级到虚拟化。

## apply（修正，2026-10-30）：改成 IntersectionObserver 自动加载，去掉按钮

第一版是「滚到 320px 自动追加 + 底部保留按钮」。用户指出底部按钮让这件事看起来仍是手动的，
要的是纯 lazyload。改成：

- 列表底部的 `.dkf-more` 当 sentinel；`IntersectionObserver`（root = `.dkf-scroll`，
  `rootMargin: 320px`）一进入范围就 `extendList()`，不需要任何点击；
- 每次追加后 effect 重建 observer；列表不足一屏时会连续追加，直到填满视口或到底；
- 没有 `IntersectionObserver` 的环境退回原来的滚动事件判断（同一 320px 阈值）；
- 按钮与 `.dkf-more-btn` 样式删掉，footer 只留「已显示 X / N · 继续滚动自动加载…」；
- 用例改为断言**没有**手动按钮、有 hint 文案；宿主 55 + 渲染 57 仍全绿。
- 版本 0.8.1。

## apply（补充，2026-10-30）：键盘也能扩窗；跳转不再“到总数就放弃”

两个边界补掉：

1. **键盘扩窗**：时间线 / issue 列表在最后一行再按 `↓` 时先 `extendList()`，下一帧
   （`requestAnimationFrame`）把焦点交给新出现的第一行；搜索结果 `↑`/`↓` 走到已加载末尾时
   同样扩窗，并把选中下标落到追加后的第一项，另一个 effect 用 `scrollIntoView({block:'nearest'})`
   把选中行带进视口。判定抽成纯函数 `nextSearchIndex(current, length, delta, hasMore)`：
   末尾且还有结果时返回 `length`（= 追加后第一项），否则回绕。
2. **跳转等流，不再提前放弃**：目标动作还没进数据（流还没读到）时保留 `scrollTo` 等流继续送；
   目标已在数据里但被窗口挡住时，直接按索引把 `listLimit` 扩到覆盖它（一次算准）；
   只有流结束仍找不到才放弃。判定抽成 `jumpPlan(index, limit, streaming)` →
   `wait | extend | scroll | give-up`。

- 两个纯函数挂进 `__internals`，新增 2 条用例（末尾扩窗 / 回绕、四种跳转计划）。
- 修正后的实际效果：流冷读期间（约 120ms）搜索并跳到一条老动作也不会静默失败——
  effect 会等流把那一行送进来再滚；100 条以外的搜索结果可以一路用方向键走下去。
- 已知仍不覆盖：如果**行筛选**把目标动作筛掉了，索引里找不到它，跳转仍会放弃（筛选是你显式开的）。
- 宿主 **57** + 渲染 **57** 用例全绿；版本 0.8.2。
