# 关系图在几十到上百节点时的可读性

## 背景

`kiln-relation-graph` 之后关系页能出真图了（`~/kiln`，58 issue / 73 边，截图见 issue 讨论）。
图能显示、点节点能聚焦、能缩放平移——**但“能看”和“读得懂”之间还差一层**：现在是一张横着
铺开的长图，缩到一屏就看不清 id，放到 100% 就得左右拖。

本条只谈**大规模下的可视化**，不改数据面，也不改“点节点 = 聚焦”的既定手势。

## 现象（都来自 `~/kiln` 实测）

| # | 现象 | 数字 |
| --- | --- | --- |
| 1 | **弱关联淹没了结构**：`relates-to` 占全部边的七成，图上都是横跨整屏的细线 | 53 / 73 = 73% |
| 2 | **近半节点只挂在弱边上**：有向边（`caused-by` / `blocks` / `part-of`）只碰到一半节点 | 26 / 58 被有向边触及 |
| 3 | **边缘节点多**：只连一条边的、完全孤立的，加起来占四成 | 度 1：18；度 0：6 |
| 4 | **宽高比失衡**：`flowchart LR` 在几百像素宽的侧栏里横向铺开；Pele 只在 < 640px 时自动转 TB | 最大度 9，平均度 2.5 |
| 5 | 边标签逐条重复（满屏 `relates to` / `caused by`），信息密度被稀释 | — |

结论：**问题不是“节点太多”，是弱边太多**。只留有向边时是 20 条 / 26 节点，是个能一眼看完的骨架。

## 目标

50–200 节点时仍然：一屏能看出骨架、能定位某个 issue、能看出焦点周围的一圈。

## 选项空间

| 方向 | 做法 | 代价 |
| --- | --- | --- |
| A 过滤 | 关系类型开关（默认只画有向边，或按强弱分层），一键“显示全部弱关联” | 容易让人以为关系不存在——需要显式计数“还有 53 条弱关联” |
| B 取景 | 默认全图不变；新增“只看焦点一跳”，或反过来默认 1 跳 + “展开全部” | 默认裁会丢掉“全景”，与上一条 issue 的假设 5 冲突，需重议 |
| C 布局 | 方向可选（LR / TB）；或按 domain 切 `subgraph` 减少跨域长边 | subgraph 会改布局；domain 只有 1 个时无效 |
| D 视觉 | 边标签只在该边与焦点/hover 相关时显示；弱边更细更淡；节点标签在小比例下退化 | 需要知道缩放比例，Pele 的 zoom 有 `scale` 可读 |
| E 交互 | hover 高亮邻域；双击节点以它为根重排；面包屑回退 | 双击与 Pele 自带的“双击缩放”冲突，要避让 |
| F 规模 | 超阈值时默认 1 跳 + 提示 | 与 B 合流 |

## 边界

- 不改数据面（仍是 `kiln graph --json` 的快照）；
- 背景布局仍不跳：**只有显式操作**（切取景、换根）才允许重排；
- 不引新依赖：布局能力已由 Pele 提供；
- 不为了好看伪造关系（不删边、不合并节点）。

## 验收草案

1. `~/kiln` 58 节点：默认视图下不看拖动也能读出“哪几个是枢纽”，且能一眼找到任意指定 issue；
2. 弱关联可一键显隐，隐藏时**明说**隐藏了多少条；
3. 聚焦后焦点一圈在屏幕上清晰可辨（现状是淡化到 22%，与外周区别够不够要看实图）；
4. 切焦点仍不重排（沿用上一条 issue 的验收）；
5. 100 节点的合成用例仍可交互（滚动/缩放不卡）。

## 待定

1. 默认视图：全图（现状）还是“有向骨架”？
2. 弱边的表达：默认隐藏、默认淡化、还是折成“+N”？
3. 是否要按 domain 分组，还是等仓库有多个 domain 再说；
4. hover 高亮邻域值不值得做（与“点节点 = 聚焦”会不会打架）。

## collect：度数分布与“只留有向边”的投影

命令（`~/kiln`，只读）：

```powershell
kiln graph --json   # nodes 58 / edges 73；逐边累计度数
```

| 指标 | 值 |
| --- | --- |
| 节点 / 边 | 58 / 73（平均度 2.5，最大度 9） |
| 度 0（孤立） | 6 |
| 度 1 | 18 |
| 度 2–3 | 17 |
| 度 ≥ 4 | 17 |
| 边类型 | `relates-to` 53、`caused-by` 19、`blocks` 1（无 `part-of`） |
| 有向边触及的节点 | 26 / 58 |

**投影**：只画有向边 → **20 条边 / 26 个节点**（边减 73%，节点减 55%）。
也就是说默认收窄不是“少画一点”，是把图从“一团”变成“一张骨架”——
剩下 32 个只挂在弱边上的节点，正好是“可折叠”的那一层。

副作用要一起记：这 32 个节点若默认不画，它们与任何东西的关系就看不见了。
所以过滤必须**显式**（开关 + “还有 N 条弱关联 / N 个节点”的计数），不能悄悄消失。

## 落地（apply）：先做方向（选项 C）

按“先看效果再决定”的顺序，只做了**布局方向可选**这一档（用户指定：屏幕可以垂直滚动）：

- 关系页顶部多一排「横向 / 纵向」，映射到 `flowchart LR` / `flowchart TB`；
- 方向进 `viewStates.graphDirection`，按仓库记忆，与取景一起恢复；
- 方向是**唯一**会改 mermaid 文本的操作（`buildMermaid(issues, relations, direction)`），
  因此也是唯一允许重排的显式操作——切焦点仍然只改 class；
- 换方向会重新 mount，**缩放会回到 fit**，这是预期的（换了布局，旧视口没有意义）。

测试：`plugin/test/render.mjs` 19 例（新增“方向只换方向词”——除首行外文本必须逐字相同，
防止换方向时连带改了节点/边）。

**没做**：选项 A（弱边过滤）、D（标签按需）、E（hover 高亮）。它们的取舍还挂在下面「待定」里。

## 落地（apply）：结构 / 全部（选项 A1）

第二次落地，做的是**默认只画有向关系**：

- 关系页图取景多一组「结构 / 全部」，默认**结构**：只画 `caused-by` / `blocks` / `part-of` /
  `supersedes`，无向的 `relates-to` 连同“只挂在它上面”的节点（按边端算，未被任何有向边触及的）
  一起收起；
- 收起时**必须报数**：图下一行「已隐藏 53 条弱关联（无向）、32 个只挂在弱关联上的 issue」，
  带一个「显示全部」按钮——不能让人以为关系不存在；
- 范围进 `viewStates.graphScope`，按仓库记忆；与方向一样属于显式重排；
- `buildMermaid(issues, relations, direction, scope)` 返回里带 `hidden: {edges, nodes}`，
  数字直接从同一份数据算出来，不另外数。

测试：`plugin/test/render.mjs` **20 例**（新增两条：结构取景不含 `---`、隐藏计数正确；
全部取景把弱边与孤立点放回来且不再提示隐藏）。

## test：在 `~/kiln` 的真实数据上验一遍

要紧的不是“算式对不对”，而是**插件自己生成的文本**（不是我在探针里另写一份）在真实仓库上是什么样。
做法：把 `kiln graph --json` 的快照塞进 `KilnView` 的假 React 里渲染出 `data-mermaid`，
再交给 vendored Pele 渲染，量包围盒与交叉：

| 取景 | 节点 | 边 | 画布 | 交叉 |
| --- | --- | --- | --- | --- |
| 结构（新默认） | 26 | 20 | 2578×468 | **0** |
| 全部（旧默认） | 58 | 73 | 4538×2018 | 112 |

- 结构取景的文本里**不含 `---`、不含 `relates-to`**——过滤发生在生成层，不是渲染后遮盖；
- 数字与 collect 里手写变体的测量完全一致（26/20、2578×468、0），说明实现与实验口径没漂；
- 高度 2018 → 468：`~/kiln` 的图从“要拖三屏”变成“一屏能看完”。

## test：聚焦一个只挂弱关联的节点，它自己会从图上消失

结构取景筛节点的口径是“被有向边触及”。焦点若正好是那 32 个只挂 `relates-to` 的节点之一：

- 焦点节点**不在文本里**（`n_c["c"]` 不存在）；
- 容器上仍挂着 `data-focus="c"`，`paintFocus` 只能淡化它的邻居，
  结果是“点了 c、图上找不到 c”；
- `~/kiln` 里这种节点有 32 个（55%），从列表取景聚焦后再切回图就会踩到。

用例：`plugin/test/render.mjs`「聚焦一个只挂弱关联的节点：它自己也必须在图上」，当前**失败**。
结论：结构取景需要一个“焦点优先”的例外——但**不能**让 mermaid 文本普遍依赖焦点
（那会让每次切焦点都重排，破坏 `kiln-relation-graph` 的验收）。

## 落地（apply）：焦点优先的例外

改法是**局部**放宽，不是让文本普遍跟着焦点变：

- `GraphPanel` 先判断“焦点被结构取景挡住了吗”（`touchesDirected`）；
- 挡住了就**这一次**按「全部」生成文本，并在图下说明「焦点 x 只挂在弱关联上，已临时按「全部」画」；
- 没挡住时文本与焦点无关——`kiln-relation-graph` 的“切焦点不重排”验收仍然成立；
- 点的还是同一个焦点：从列表聚焦一个弱关联节点、再切回图，不会再“点了它却看不见它”。

用例转绿（21 个渲染用例），并额外断言那句说明必须出现——临时放宽不能悄无声息。

## 落地（apply）：焦点取景——重画，而不是淡化

第三种取景（用户提出）：**以焦点为中心重新绘图，只画有关系的 issue**，同时把“全局淡化”保留成另一档。

- 范围变成四档：**自动**（默认）/ 结构 / 全部 / 焦点；
- 焦点取景：只留焦点与它的一跳邻居（任意关系类型，含 `relates-to`），整张图重排；
- 这一档**关掉淡化**（`tiers = null`）：屏幕上剩下的本来就都是相关节点，再分档是多余信息；
- 没聚焦就选「焦点」：退回结构取景并提示“先选一个 issue”，不拿「全部」糊人；
- 结构 / 全部两档继续用“淡化”那套（原来的方案没动），想要“保持位置、只做视觉强调”的人仍然有；
- 代价写在明处：焦点取景**每次换焦点都重画**（缩放回 fit），与结构取景“切焦点不动布局”正好相反。

测试：`plugin/test/render.mjs` **24 例**，新增三条：焦点取景只留一跳（`c` 因为不与 `b` 相邻被排除）、
无焦点时退回结构取景、“结构取景切焦点不动文本 / 焦点取景换焦点必须重画”这一对相反性质。

## 落地（apply）：自动取景——默认值跟着状态走

实测下来两种取景各自只擅长一种状态，所以默认值不该是常数：

| 状态 | 默认取景 | 理由 |
| --- | --- | --- |
| 无焦点 | **结构** | 全局要的是“一眼看骨架”，58 节点全画出来是 4538×2018、112 个交叉 |
| 有焦点 | **焦点** | 聚焦要的是“看清这一圈”，重画一张一跳子图（中位 3 个节点）比淡化准得多 |

于是范围改成四档 **自动 / 结构 / 全部 / 焦点**，默认「自动」：

- 自动 = 上面的表；手动选结构 / 全部 / 焦点则固定下来，不跟着焦点变（存进 `viewStates.graphScope`）；
- 因此**默认路径下“聚焦”会重排**（这是要的效果），而“切焦点不动布局”变成显式结构/全部两档的性质；
  `kiln-relation-graph` 的验收相应理解为“结构取景下不重排”，不是“任何时候都不重排”；
- 自动档下仍保留两条兜底：焦点在结构外（32 个弱关联节点）时结构取景临时放宽到全部；
  选了焦点却没有焦点时退回结构。

测试：`plugin/test/render.mjs` **25 例**，新增“自动取景：无焦点用结构、有焦点用焦点”，
其余用例改为显式传 scope，避免默认值变化把断言测成空转。

## 落地（apply）：拆成「边」与「聚焦时」两组，去掉「自动」

上面两节的四档取景**已被这一节取代**——不是命名微调，是维度拆解。

**先纠一个事实**：这一档留的是**有向**关系（带方向的声明），不是“强关系”。
按词表，强关系是 `ordering` 槽的 `part-of` / `blocks`，而 `caused-by` 属于 `lineage` 槽（弱）却**留着**。
`~/kiln` 若真只画强关系只剩 `blocks` 1 条边、2 个节点，没有意义。所以叫「强关系」会是假名。

四档按钮的毛病是把两个维度压在一排里，于是「结构」既像筛边又像换布局。现在拆开：

| 控件 | 选项 | 含义 |
| --- | --- | --- |
| **边** | `有向`（默认）/ `全部` | 只画带方向的声明，或连无向的 `relates-to` 一起画 |
| **聚焦时** | `重画`（默认）/ `淡化` | 以焦点为中心重画一圈，或保持原图只淡化圈外 |

「自动」去掉——它本来就是这两者的组合规则，现在由两条默认值表达：
**没焦点看有向全图，有焦点重画一圈**。`viewStates` 里对应 `graphEdges` / `graphFocusMode` 两个键。

边界行为（都会写在图下，不静默）：

- 焦点只挂无向关联、而边筛选了「有向」时，重画那张**临时放开筛选**并说明；
- 边筛选了「有向」且没在重画时，明说「隐藏 N 条无向关联、M 个只挂它们的 issue」，带「显示全部」；
- 淡化档不重排，文本与无焦点逐字相同；重画档换焦点就重画（缩放回 fit）。

测试：`plugin/test/render.mjs` **24 例**，覆盖四组控件、两档聚焦行为、切焦点的两种相反性质。






## collect：四种减噪手段的实测（58 节点）

方法：同一张 `~/kiln` 图（58 节点 / 73 边），用 vendored Pele **在 Node 里直接 `render()`**
（不需要浏览器，跑的是插件里同一份代码），量三样：包围盒、边交叉数（节点中心连线近似，
共用端点的边不计）、渲染耗时。

| 策略 | 画布 | 交叉 | 节点 / 边 | 耗时 |
| --- | --- | --- | --- | --- |
| TB 全图（当前默认） | 4538×2018 | 112 | 58 / 73 | 20 ms |
| ＋紧凑间距（nodeSpacing 15 / rankSpacing 30） | 4087×1699 | 107 | 58 / 73 | 9 ms |
| ＋去边标签 | 3995×1680 | 98 | 58 / 73 | 5 ms |
| **只留有向边** | **2578×468** | **0** | **26 / 20** | 2 ms |
| 只留有向边 ＋ 无标签 | 2578×372 | 0 | 26 / 20 | 1 ms |
| LR 全图（对照） | 4243×2240 | 112 | 58 / 73 | 6 ms |

**结论：间距和标签各只值 10% 左右，过滤值一个数量级**——高度 2018 → 468，交叉 112 → 0。
换个说法：现在这张图的乱，73% 是 `relates-to` 造成的，调参救不了。

三条顺手量到的：

1. **`flowchart-elk` 等于没换**：同一张小图，`flowchart TB` 与 `flowchart-elk TB` 的节点坐标逐点相同
   → Pele 把它当同一套布局（`detectType` 认这个类型，但没有独立的 ELK 引擎）。**换 ELK 不是可选手段。**
2. **一跳很小**：任一节点为焦点时，子图中位 **3** 个节点、平均 3.5、最大 10。
   在 58 节点下“聚焦即收窄”几乎不损失上下文——最省事的取景规则。
3. **边能单独定位**：Pele 给每条边挂了 `data-id="L_<from>_<to>_<序号>"`（节点是 `data-id="<node>"`），
   所以“聚焦时只淡化无关边”是能做的。`kiln-relation-graph` 里“边没有抓手”的结论是错的，需回补。

复现（不进仓库，用完即删）：`kiln graph --json > graph.json`，再用 `plugin/lib/client.pele.js`
导出 `render()`，对同一份节点/边拼出不同变体逐条量。交叉数是直线近似，只用于同条件横比。

### 候选手段与代价

| 手段 | 实测效果 | 成本 | 风险 |
| --- | --- | --- | --- |
| **A1 默认只画有向边**，一键展开弱关联 | 交叉 112 → 0，高度 −77% | 低 | 必须显式说“隐藏了 53 条 / 32 个节点”，否则像关系不存在 |
| A2 按关系类型逐个开关（词表 5 组） | 同 A1，更细 | 中 | 5 个开关 + 状态记忆，控件比 A1 重 |
| **B1 聚焦即收窄到 1 跳** | 节点 58 → 3（中位） | 低 | 与“默认全图”冲突，得重议上一条 issue 的假设 5 |
| B2 超阈值才自动 1 跳（如 > 40 节点） | 小图不受影响 | 低 | 阈值是魔法数，要能手动推翻 |
| D1 边标签按需显示 | 交叉 −14%，画布 −12% | 低 | 布局仍会变（标签宽度影响 rank） |
| D2 紧凑间距 | 画布 −10% | 低 | 一行 frontmatter config |
| D3 聚焦时淡化无关边（`data-id`） | 纯视觉降噪 | 中 | 需回补 `kiln-relation-graph` 的限制 |
| E1 hover 高亮邻域 | — | 中 | 与“点节点 = 聚焦”并存，不冲突 |
| F 按 domain 分组 | 不适用 | — | `~/kiln` 只有 1 个 domain，等有多个再谈 |

**推荐顺序**：A1（一发就把图从“一团”变“骨架”，且可逆）→ D3（边跟着焦点走，纯视觉）
→ B2（只在超大图时兜底）→ D1/D2（调参，最后做）。




## collect：别的工具怎么做“聚焦一个节点”

用户提的线索：「有向」其实只是**把无向关系藏起来**，所以名字是假名；另外「全部 + 重画」这一格不兼容。
先看别人怎么解决同一类问题（多节点关系图里聚焦某点）。

### 四种做法（不是一个旋钮，而是四种不同的机制）

| 家族 | 代表 | 机制 |
| --- | --- | --- |
| **换视图** | Obsidian 的 **Local graph**（独立命令 + depth 滑块）、[Graph+ 的 local pane](https://github.com/woodamsclark/graph-plus) | 不是在同一张图上淡化，而是**另开一个只画邻域的视图**；焦点自动跟随活动笔记，相机/过滤器/选择各自独立 |
| **过滤成 ego network** | Gephi 的 **Ego Network** 过滤器（depth k + include self） | 按“从焦点出发 k 跳”裁剪图，其余**根本不画** |
| **高亮 + 淡化** | XState 可视化器（只亮当前 state 与被触发的迁移）、[VHDL FSM 图](https://marketplace.visualstudio.com/items?itemName=Bastocus.vhdl-fsm-diagram)（点 state 亮它所有进出边、其余变暗）、Obsidian 的 hover 高亮 | 图不重构，只改不透明度/颜色 |
| **focus+context 变形** | Furnas 的 fisheye、Sarkar & Brown 的双曲视图 | 不删不改，靠几何变形把焦点放大、远处压缩；工程上少见 |

对照我们的两档：**重画 = 换视图 + ego network（depth 1）**，**淡化 = 高亮+淡化**。两者都是成熟做法，
坏的不是机制，是**把两套机制的自由组合当成了两个正交旋钮**。

### 值得直接借鉴的四点

1. **depth 滑块**：Obsidian 的 local graph 有 depth（每加一层显示上一层节点的邻居），
   而[实践建议是“打开 local graph、depth 设 2”](https://github.com/undefined-ui/second-brain-os/blob/main/docs/05-graphs/obsidian-graph-view.md)。
   我们的「一圈」现在固定 1 跳，`~/kiln` 上有向邻居中位是 0——1 跳看不到“来龙去脉”，2 跳才有链。
2. **语义缩放 / 标签门槛**：Obsidian 的 “Text fade threshold”、某规范的
   [zoom-responsive labels](https://github.com/chipi/podcast_scraper/blob/main/docs/architecture/VIEWER_GRAPH_SPEC.md)
   （缩放 < 0.5 不显示标签、0.5–1.0 短标签、> 1.0 全标签），以及某个真实 PR 里的策略：
   “除 hover / 焦点 / 焦点邻域 / 高度数节点外不显示标签”。
   我们的标签是**永远全显示**，这在小比例下就是满屏噪点。
3. **hover 预览**：Obsidian 悬停即高亮该节点的连接，不用点。我们现在点才聚焦，悬停无反馈——
   而 `data-id` 已经在 DOM 上，成本很低。
4. **方向是显示开关，不是筛选**：Obsidian 面板里 “Arrows” 是 Display 里的开关，Tags/Orphans 在 Filters 里。
   这印证了用户的判断：我们那个「有向」开关本质是**隐藏无向边**，属于“显示”，不该叫“筛边”。

### 命名：说清楚“藏的是什么”

既然藏的就是无向的 `relates-to`，名字应该点它：

| 候选 | 说明 |
| --- | --- |
| `无向关联：隐藏 / 显示` | 最准；与 kiln 词表 `relates-to` 对得上 |
| `只画有向 / 含无向` | 也准，但仍是“维度的名字”而不是“藏了什么” |
| `箭头`（Obsidian 用词） | 简短，但那是“是否显示箭头”，与“是否隐藏无向边”不完全等价 |

### 一个更省事的收敛：把旋钮换成视图

上面四种工具**没有一个是让用户自由组合两个维度的**：Obsidian 是“全局 / 局部”两个视图 + 一个过滤器面板；
Gephi 是“视图 + 过滤链”。据此可以把我们的两排按钮收敛成：

| 视图（三选一） | 内容 |
| --- | --- |
| **全局** | 整张图，不淡化（对应现在的“有向 + 无焦点”） |
| **全局 + 焦点** | 整张图 + 淡化圈外（用户觉得最好用的那格） |
| **焦点一圈** | 只画焦点邻域（depth 可选 1/2） |

外加一个独立的**显示开关**：`无向关联 开/关`（任何视图下都可用），
它不再是“取景”的一部分，而是“图里要不要出现无向边”。

这样「全部 + 重画」这样的格子**根本不出现**——不是禁用，而是没有这个组合。

## 落地（apply）：视图 + 开关，取代两排旋钮

按调研的结论重做交互（用户定的方向：拆成两组后继续收敛）：

| 控件 | 选项 | 说明 |
| --- | --- | --- |
| **视图** | `全局` / `全局+焦点`（默认）/ `焦点一圈` | 三个有名字的视图，取代原来的「淡化/重画」两档 |
| **无向关联** | 开 / 关（默认关） | 不是筛边维度，只是一个显示开关：要不要画 `relates-to` |
| **半径** | `1 跳`（默认）/ `2 跳` | 只在「焦点一圈」下出现 |

- 「全部 + 重画」这个格子**不存在**了——不是禁用，是没有这个组合；
- 「有向」这个名字去掉了：它本来就是在**隐藏无向边**，现在就叫「无向关联」开关；
- 焦点一圈用 `egoNodes` 做 BFS（`depth` 跳），边取“两端都在圈内”的那些；
- 焦点只挂在无向关联上、而开关是关的：这一张临时放开并说明（否则空图）；
- **边现在也会淡化**：Pele 的边带 `data-id="L_<from>_<to>_<n>"`，两端都在圈外才淡，
  解决“亮线连着暗节点”的错位。

测试：`plugin/test/render.mjs` **25 例**（视图三档、无向开关、1/2 跳、淡化档不重排 / 一圈档必重排、
2 跳多出第二层）。

## test：在 `~/kiln` 上跑三种视图

同一份 `kiln graph --json` 快照，喂给插件自己的组件渲染出 `data-mermaid`，再交给 Pele：

| 视图 | 节点 | 边 | 画布 | 交叉 |
| --- | --- | --- | --- | --- |
| 全局+焦点（无焦点） | 26 | 20 | 2578×468 | 0 |
| 全局+焦点 ＋ 无向 | 58 | 73 | 4538×2018 | 112 |
| 焦点一圈 1 跳（枢纽 `cli-necessity`） | 10 | 9 | 1728×250 | 0 |
| 焦点一圈 2 跳（同一枢纽） | 28 | 33 | 2801×629 | 10 |

把 58 个节点各自当作焦点的**邻域规模**（BFS，含焦点自己）：

| 边 | 1 跳 | 2 跳 |
| --- | --- | --- |
| 有向 | 中位 **1**、p90 3、最大 6 | 中位 1、p90 6、最大 9 |
| 含无向 | 中位 3、p90 6、最大 10 | 中位 10、p90 19、最大 29 |

三条结论：

1. **「一圈」必须搭配无向**：只画有向时中位只有 1 个节点（就是焦点自己），这一档等于没用——
   所以“焦点只挂无向关联时临时放开”的兜底不是边角料，是常态路径。
2. **2 跳是这一档的上限**：含无向时 p90 已到 19 个节点，再放就回到“一团”。
3. 枢纽节点（10 → 28 个节点）说明 1/2 跳的选择在真实数据上差异很大，滑块必须给。

## 结论

关系页的图交互收敛成一句话：**三个有名字的视图 + 一个显示开关 + 一个半径**。

- 视图：`全局` / `全局+焦点`（默认）/ `焦点一圈`；
- 无向关联：开关，默认关（关掉的是 `relates-to`，不是“弱关系”——它是唯一无向的那类）；
- 半径：一圈视图下 1 / 2 跳，默认 1；
- 淡化档不动文本、只动 class（节点与**边**都淡）；一圈档换焦点就重画。

这条 issue 里验证过、但**没做**的两项，留给下一个：

1. **语义缩放 / 标签门槛**：Obsidian 的 text fade threshold 那类做法——小比例只显示短名，
   放大再显示全名。现在的标签永远全显示，是剩下最大的一块噪声；
2. **hover 预览**：悬停即高亮该节点的连接，不用点击。`data-id` 已在 DOM 上，成本低。

明确**不做**的：`flowchart-elk`（Pele 没有独立 ELK 引擎，坐标逐点相同）、力导向布局（Pele 只有分层布局）。

## 结论（补充）：视图收敛到两个

上面“三视图”再砍一刀：`全局` 与 `全局+焦点` 只差一个淡化，没必要并列——**淡化是全局视图在“有焦点”时的表现**，不是另一档。

| 视图 | 行为 |
| --- | --- |
| **全局**（默认） | 整张图；有焦点时淡化圈外（节点与边都淡），没焦点时就是整张图 |
| **聚焦** | 以焦点为中心重画，只画 `depth` 跳内的邻域（1 / 2 跳），换焦点即重排 |

「无向关联」开关保留，两个视图都可用；切到「聚焦」而还没有焦点时，退回全局并提示先选一个 issue。

## 结论（再收敛）：去掉「无向关联」开关

「全局」在有焦点时本来就会把无关节点淡化，所以**焦点的无向邻居不需要开关也能体现出来**——
它们和相关节点一样是亮的。开关因此多余：

| 状态 | 画什么 |
| --- | --- |
| 无焦点 | 只画有向关系（骨架：26 节点 / 20 边，交叉 0） |
| 有焦点 | 有向骨架 ＋ **焦点自己的无向邻居**；圈外一律淡化 |

规则变成一句话：**无向边只在“焦点需要它”的时候出现**，没有开关可点。

代价要记住：**「全局」视图切到一个有无向邻居的焦点时，文本会变、布局会动**——
这与之前“全局视图切焦点不重排”的验收不再一致（只有焦点没有无向邻居时才逐字不变）。
这是用户主动选的取舍：宁可布局动一下，也不让“相关但无方向”的那一圈消失。
