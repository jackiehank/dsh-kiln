# kiln-input-streams — 时间线之后，剩下哪几路输入还在整份缓冲

- **domain**：integration
- **关联**：part-of `kiln-many-issues`；relates-to `kiln-v030-adapter`（时间线流已落地）、
  relates-to `kiln-perf-snapshot`（快照的取数成本）

## 问题

`kiln-v030-adapter` 把时间线改成了流式：宿主 spawn `kiln action log --jsonl`，一行一个动作，
边读边发，EOF 收口。于是 `kiln-many-issues` 里“timeline 流”那一项不再欠账。

但**插件还有四路输入是整份缓冲**，它们各自在什么规模下开始疼、该用流式还是分页、上游缺什么、
插件侧要不要改传输，都还没定：

| # | 输入 | 产出方 | 插件怎么用 | 现在的形态 |
| --- | --- | --- | --- | --- |
| 1 | **索引** `kiln list --json` | 上游 `writeJSON` | 将来做 issue 列表窗口 / 按最近排序 | 一份 JSON 文档；无 `date`、无 `limit/offset` |
| 2 | **关系图** `kiln graph --json` | 上游 `writeJSON` | 关系页全局图；快照的节点与边来源 | 一份 JSON 文档；`--issue/--depth` 只是收窄输出，**仍 build 全仓** |
| 3 | **详情** `kiln path <id> --json` | 上游 `writeJSON`（单条） | 按需详情（还没做）/ issue 页动作链 | 一份 JSON 文档；一个 issue 的动作越多，单条文档越大 |
| 4 | **插件传输** `GET /kiln/flow` | 宿主组装 | 三页的 `issues + edges` 快照 | 一份 JSON 文档，HEAD 变了整份重发 |

时间线已经证明“NDJSON + 逐条 flush + 断连即 kill”在插件里可行；现在要回答的是**其余四路是否值得照做**，
还是“上游给窗口/分页 + 宿主只取一页”更划算。这不是纯上游问题：既可能上游加 `--jsonl/--limit`，
也可能插件自己分帧，两条路的代价与验收差很多。

## 现状与边界

- 流式不是免费的：一行一行发意味着**没有“完整文档”可言**，收口要靠 EOF/退出码；
  如果消费方需要“总计 / 排序 / 筛选”，全量仍然跑不掉，流式只买到“首屏早一点”。
- 索引天然要全量才能排序与筛选；`list --json` 缺 `date`（按最近排序）与 `limit/offset`（翻页），
  这两项是 `kiln-many-issues` 已经点名、v0.3.0 复验仍缺的上游缺口。
- 关系图页画的其实只是快照里的 ≤80 个节点（`buildFlow` 截断后再滤边，见假设 §0），
  所以这一路要讨论的不是“把 graph 改成流式”，而是“这 80 个名额怎么选、第 81 个怎么打开”。
- 详情这一路要先有端点（`GET /kiln/issue`），才谈得上它的传输形态；它同时决定
  “快照外的 issue 能不能聚焦”（见 `kiln-v030-adapter` 的已知代价）。
- 约束照旧：只读、不落盘、不在插件里复刻 kiln 的解析、数据只走 `kiln <cmd>` 子进程。

## collect（2026-10-28）：四路输入的量级与上游实现

### 1. 实测（kiln v0.3.0，`~/kiln`：70 issue / 350 动作；耗时是 5 次中位数）

| 输入 | 字节 | 折合 | 中位耗时 |
| --- | --- | --- | --- |
| `list --json` | 22,920 | 327 B / issue | 111 ms |
| `graph --json` | 33,576 | 480 B / issue | 114 ms |
| `graph --issue action-log --depth 1 --json` | 2,414 | 3 节点 / 2 边 | **114 ms** |
| `path action-log --json` | 4,351 | 单条 issue | 115 ms |
| `path --all --json` | 168,106 | 480 B / 动作 | 148 ms |
| `action log --jsonl` | 100,768 | 288 B / 动作 | 115 ms |
| `list --search=kiln --json` | 17,490 | 命中数决定 | 111 ms |

本仓（22 issue / 146 动作）同口径：`list` 7,484 B / `graph` 10,410 B / `path --all` 74,324 B /
`action log` 41,834 B；小仓上四路的耗时都落在进程启动的 ~100ms 地板上，**看不出字节数的影响**。

外推到 100k（按上面每行/每动作的实测比例，不是旧估算）：

- `list --json` ≈ **32 MB**（0.33 KB/issue）；
- `graph --json` ≈ **48 MB**（0.48 KB/issue）；
- `path --all` ≈ **48 MB**（0.48 KB/动作）；
- `action log --jsonl` ≈ **29 MB**，已经是流式，宿主不整份拿。

**修正**：`kiln-many-issues` 里写的「100k 索引 17MB」与这里的 32MB 对不上——那个 17MB 是当时
按 64 issue 的粗估，这次按本机逐条实测比例重算，以本表为准；结论（索引是最大的一路整份文档）
不变，只是量级更大。

### 2. 上游实现（v0.3.0，`internal/cli/cli.go`）

- `writeJSON` 的注释就是「one document on stdout」（`cli.go:3108`）——`list` / `graph` / 单条 `path`
  都走它：先在内存里拼完整份，再一次性写。
- `list --json` 先建全量 `rows` 再 `writeJSON`（`cli.go:2706` / `cli.go:2730`）；`listIssue` 没有 `date`；
  `--limit` 只服务 `action log`（`cli.go:1258`，`list --limit` 在测试里明确被拒：`cli_test.go:2246`）。
- `graphJSON` 先 `engine.IDs` + `FoldEdges` 把**全仓**折好，`--issue/--depth` 的裁剪发生在之后
  （`cli.go:2915`–`2931`），再 `writeJSON`（`cli.go:2965`）——这解释了为什么 `graph --issue`
  的输出只有 2.4KB、耗时却和全图一样（114 vs 114ms）。
- `path --all` **已经有流式 writer**（`pathBatchWriter`，`cli.go:1873`）：按 issue 逐个写进 64KB
  `bufio`，不再把整份文档憋在内存里；但单条 `path` 仍走 `writeJSON`（`cli.go:1823`）。
- `action log` 是真正的逐条 sink，`--limit` 用尽或消费方消失都能停扫（`cli.go:1344`）。

也就是说：上游已经证明「行式文档 + 边读边写」能做（`path --all` 的 writer、`action log` 的 sink），
但只用在两处；`list` 与 `graph` 还是整份，且 `list` 连分页与 `date` 都没有。

### 3. 对四路的直接含义

- **索引**：唯一同时缺 `date`、`limit/offset`、流式的输入。100k 时 32MB 要先进宿主内存再解析；
  「窗口 + 分页」比「流式」更贴近它的用途（列表要排序、要总数、要筛选完整性）。
- **关系图**：字节随 issue 线性，但更麻烦的是「全仓构建 + 布局不可读」。`--issue` 省不掉构建
  （实测同耗时），所以这一路的结论很可能是**大仓降级**，而不是把 `graph --json` 改成 NDJSON。
- **详情**：单条典型 4KB，整份就够；只有「一个 issue 上千动作」时才值得一动作一行，属于边角。
- **快照传输**：`/kiln/flow` 的 payload = 全图 + 80 条 `path`，本仓 10KB 级、`~/kiln` 74KB 级，
  **不随仓规模爆**（80 是硬上限）；它的问题是「HEAD 一动整份重发」，属于缓存帧，而不是流式。

## 要回答的问题

1. **尺子**：每一路输入，按什么指标判定“必须改”？首字节时间、首个可用屏、总时长、宿主/浏览器峰值内存，
   还是“能否在数据到齐前给用户可用内容”？给出各路的阈值（例如 100k 合成仓）。
2. **索引**：`list --json` 该加 `--jsonl`、`--limit/--offset`、还是 `--count`+窗口？
   插件侧“宿主窗口 W=100”与前端虚拟滚动分别解决哪一段？
   排序需要 `date`，这个字段放 `list` 行还是让插件按 `action log` 补？
3. **关系图**：全局图在大仓还画不画？若不画，降级形态是什么（统计/领域簇/只画焦点邻域）？
   `graph --issue` 要不要上游做“低成本邻域”（不 build 全仓），还是接受现在的 build 成本？
4. **详情**：`GET /kiln/issue` 的契约（`path` + `graph --issue --depth` 并发？分帧？LRU 键？）；
   单条 `path` 在“动作特别多”的 issue 上要不要 NDJSON（一动作一行），还是整份就够？
5. **插件传输**：`/kiln/flow` 要不要也变成 NDJSON（`nodes` 帧 / `edges` 帧 / `done`）？
   还是等上游分页后“只发一页”，保持单文档？两种方案对快照缓存（HEAD 失效、增量）的影响分别是什么？
6. **优先级**：四路里先做哪一路？以“用户能感知的收益 / 上游依赖是否就绪 / 改动面”排序，给出理由。

## 假设（2026-10-29）：详情单独取、索引等上游分页、图不再流式、快照传输保持整份

### 0. 先修正一个前提（否则整道题会问错）

关系图在插件里**从来不是全仓图**：它画的是快照里的 ≤80 个节点与这些节点之间的边
（`buildFlow` 先 `slice(0, maxIssues)`，再只留两端都在 `kept` 里的边）。所以
「`graph --json` 100k 会到 48MB」是**上游命令**的体量，不是浏览器要收的体量。插件今天真正
没解决的是两件事：**这 80 个名额怎么选**，以及**第 81 个怎么打开**。

同理，`/kiln/flow` 的 payload 有上限：全图（70 issue 时 33KB）+ ≤80 条 `path`（70 issue 时
整份 168KB），本仓/`~/kiln` 都在 200KB 量级。**它不随仓规模爆**，只随「80 条里动作多少」涨。

### 1. 尺子（回答 Q1）

| 指标 | 目标 | 依据 |
| --- | --- | --- |
| 小仓不退化 | 首屏/切页/交互 ≤0.3s，热命中 <5ms | 现有快照的实测与 `kiln-perf-snapshot` 的验收 |
| 单次输入的浏览器体量 | 任何一份响应 ≤1MB | 超过就不是「读一屏」而是「下载一份数据」 |
| 100k 索引可用 | 首个可用屏 ≤2s；宿主内存峰值 ≤~100MB | 上游 100k 的 `action log` 全量 1.35–1.68s 是同类成本的下限 |
| 100k 详情可用 | 有 loading 与取消；首个可用内容 ≤2s | `graph --issue` 在 100k 仍全仓构建（见 §6） |
| 完整性 | 筛选/排序/总数基于**完整集合**，不是「已读到的部分」 | 时间线的流式是有终点的；列表没有 |

关键区分：**时间线要的是「尽快看到第一条」**，所以流式对；**列表要的是「排序/筛选/总数」**，
半截数据给不出正确结果，流式只买到首屏、买不到正确性。两者不该用同一个交付形态。

### 2. 详情（Q4）——先做，且不需要新上游

实测单条 `path <id> --json` 已经带齐：`issue` / `action` / `done` / `actions`（`ordinal`、`commit`、
`date`、`title`、`refs`）/ `relations`（只含碰到该 issue 的边，形状与 graph 一致）。缺的只有
**邻居节点的摘要**（domain / action / done / title / tags），那正是 `graph --issue <id> --depth 1`
返回的东西（本仓 1.8KB、`~/kiln` 2.4KB）。

| 选项 | 做法 | 代价 | 风险 |
| --- | --- | --- | --- |
| **A（选）** | `GET /kiln/issue` = `path` ＋ `graph --issue --depth` 并发，两份整文档，宿主 LRU | 2 个进程（~230ms@70；100k 靠 loading） | `graph --issue` 在大仓仍全仓构建 |
| B | 只取 `path`，邻居摘要从快照/时间线流里找，找不到就只显示 id | 1 个进程 | 邻居可能只有 id，结构页缺字段；体验不稳定 |
| C | 用时间线流的行拼出该 issue 的动作链，只取 `graph --issue` | 1 个进程，动作「免费」 | 流里没有 `ordinal`/`refs`；且依赖「流已读完」，两套口径 |

**选 A**，理由：详情是「点开一条、要把话说全」，权威性优先于省一次进程。B 作为 A 的降级路径
（图取不到时仍显示动作链）；C 否决——它把「详情」变成「流的一个视图」，而流会被切页 kill，
用户点开时不一定完整。

这条一次解决三处死路：**快照外聚焦**、**搜索结果展开**、**issue 页第 81 条以后**（列表本身
仍受索引限制，见 §3）。

### 3. 索引（Q2）——等上游，先不做半截

今天 issue 页的列表**根本没有调 `list`**：它用的是 graph 节点的 id 序前 80。所以「索引」是
新工作，不是改造既有调用。

| 选项 | 做法 | 完整性 | 上游依赖 | 评价 |
| --- | --- | --- | --- | --- |
| A | 上游加 `list --jsonl`，一行一个 issue | 行式，需读完才知道总数 | 新子命令 | 首屏早，但排序/筛选/总数仍要等全量；UI 会出现「总数未知」 |
| **B（选）** | 上游给 `list --json` 加 `date`（末条动作 author date）＋ `--limit/--offset`（或 `--count` + `--sort=recent\|id`） | 宿主持有全量索引，浏览器只收窗口 | 两个字段/参数 | 语义最干净：排序、筛选、翻页都在宿主完成 |
| C | 插件从 `action log` 反推索引（id / 最近动作 / 日期 / 标题 / domain） | 缺 `done` 与 issue 级 tags | 无 | 要复刻「终点动作」判定，违反「不在插件里复刻 kiln 状态」；标题口径也要与 `list` 对齐 |
| D | 宿主全量 `list` 后只回窗口 | 完整 | 只要 `date` | 有 `date`、还没分页时的中间态；100k 时宿主吃 32MB，可接受一次 |

**选 B**；D 是 B 落地前的中间态（先解决「浏览器不收 32MB」，宿主慢一点可以接受）。
C 只在「上游短期不给任何东西」时作为应急，且必须只用于「最近动作」排序，不参与 done/筛选。

**没有 `date` 之前不做窗口**：按 id 序翻页会丢掉「最近」这个唯一有意义的排序，等于把截断
从 80 条挪到 100 条，问题没解。

> **修订（2026-10-29）**：issue 列表可以改由 `action log` 流折叠出来，本节降级为「大仓窗口 /
> 权威校验」——列表的正确性不再依赖上游 `date`。见文末「假设修订」。

### 4. 关系图与快照传输（Q3、Q5）——不做流式

- **图**：已经受 80 上限约束，改 NDJSON 只是把「80 个节点 + 边」拆成帧，浏览器一样要等布局；
  Pele 是分层布局，流式画到一半会重排。结论：`graph --json` 不改流式。
- 真正要定的是**名额策略**：现在按 id 序取前 80（graph 的稳定序），大仓里「最近在动」的 issue
  很可能排在第 81 位之后。等索引有 `date` 后，把快照名额改成「最近 N + 焦点邻域 + part-of 伞」；
  在那之前不改，只把「已截断、共 N 条」的提示写清楚（已有）。
- **传输**：`/kiln/flow` 保持单文档。理由：体量 200KB 级且不随仓增长；一份快照 = 一个 HEAD
  缓存键，是现有缓存与增量的基础；改成 NDJSON 要把「半份快照」的状态机也引进来，收益只在首屏。
- 详情与索引各自是**新端点**（`/kiln/issue`、将来的 `/kiln/index`），不把 `/kiln/flow` 改成通用流。

### 5. 顺序与依赖（Q6）

```text
详情端点（无上游依赖）
   ├─ 解锁：快照外聚焦 / 搜索命中展开 / issue 页 81+ 的详情
   └─ 提供：图截断策略需要的「按需邻域」取数口
图截断策略（名额选择，依赖将来的索引 date；可先只做可见提示）
索引窗口（依赖上游 date + limit/offset）
   └─ 传输收口（/kiln/index 或 /kiln/flow?offset&limit，随索引一起）
```

先做详情的三个理由：用户可感知（三处死路一次解开）、不阻塞于上游、改动面集中在一个新端点 + 客户端合并。

### 6. 风险与证伪条件

1. **`graph --issue` 在 100k 的成本未测**：70 issue 时 114ms（与全图同值，因为它先折全仓）；
   上游 perf 数据 4000 动作时 277ms。若 100k 实测 >2s，详情必须「先画动作链、图后到」，
   并把上游「低成本邻域」从可选升为必需。
2. **单条 `path` 的边角**：通常 4KB，但「一个 issue 上千动作」时会膨胀。先整份；若实测 >1MB，
   再推动上游 `path <id> --jsonl`（一动作一行）。
3. **索引的 `date` 语义**：末条动作的 author date，merge 仓不是严格全局时间序；翻页边界可能抖动，
   与既有排序约束一致，需在 UI 说明是「拓扑约束下的 author-date」。
4. **证伪条件**：若上游只给 `list --jsonl` 而拒绝 `limit/offset`，本裁决的 B 不成立，需要重估
   （行式 + 宿主累积 + 浏览器窗口，可能退回 D 的变体）。
5. **详情缓存键**：HEAD + depth + id；HEAD 被改写即清，不做 stale 复用。

## 假设修订（2026-10-29）：issue 页复用同一条流——列表、色条、done 都能从流里长出来

### 0. 结论

采纳。issue 页在**无焦点**时默认按最近动作倒序，而 `action log` 流就是全仓动作的 author-date
倒序——把流按 issue 折叠一次，就能得到与 `list --json` 同口径的列表（顺序、标题、领域、标签、
done、色条），**不多起一个进程**，也不等上游的 `date/limit`。

本仓 70/70 条 issue 的对照实验（`~/kiln`，v0.3.0，2026-10-29）：

| 折叠出来的量 | 对照 | 结果 |
| --- | --- | --- |
| 每个 issue 的**首现**动作与 commit | `list --json` 的 `action` / `commit` | 70/70 一致 |
| 首现顺序 | author-date 倒序 | 严格单调，无逆序 |
| `domain`（首个非空） | `list --json` 的 `domain` | 70/70 一致 |
| `tags`（全量并集） | `list --json` 的 `tags` | 70/70 一致 |
| `done`（首现动作 ∈ 终点词表） | `list --json` 的 `done` | 70/70 一致 |
| 每个 issue 的动作总数 | `path --all --json` 的 `actions` 条数 | 70/70 一致 |

### 1. 折叠规则（每条都对着 kiln 源码，不是猜）

- **顺序**：git 是 author-date 倒序；issue 的**首现位置**就是它的最近动作，因此首现顺序 =
  现在 `sortIssues` 的 recency 序。jj 是拓扑序，跨 issue 不保证 date-desc——需要严格时间序时
  在客户端按 `date` 再排（小仓 O(n log n) 可接受，大仓等窗口）。
- **最新动作 / 标题 / 时间**：首现行即 `p.Last()`；`issueTitle` 取 `last.Title || last.Subject`。
- **domain**：`engine.go:71` 在时间序里用**最后一个非空 domain**覆盖，流是倒序 → 取**首个非空**。
- **tags**：`appendUnique` 的全量并集；倒序累加后展示前反一次。
- **done**：`e.isDone` = `p.Last()` 属于终点词表；首现行 `action ∈ terminal` 即可判定。
  终点词表与起点动作来自 `kiln action list --json`（`names/start/terminal`，不读历史、不需要仓库），
  不把 `ask` / `apply` 硬编码进客户端。
- **色条**：每个 issue 维护一份**时间升序**的动作数组（新行往里插到头部），`strip()` 只用最近 12 格
  + older/newer 计数——流一开始就能画出色条，之后只有“+older”的数字在长。
- **ordinal**：流里没有。可以在“起点动作出现（= 该 issue 历史读完）”或 EOF 时回填总数；
  在此之前提示里省略序号即可。用户说的 `ask` 标记正是**单条 issue 的完成信号**——它在配置里叫
  `start`（本仓是 `ask`），所以判据用 `action list` 的 `start`，不用字面量 `ask`；不想要这个优化也行，
  EOF 兜底，行为只是“+older 晚一点定稿”。

### 2. 三个真约束（要在 UI 上说清，不是否决）

1. **筛选完整性**：domain / state 的 facets 和结果都随流增长；流没读完前**不能给“空结果”**。
   筛选激活时显示“已读 X 条，继续加载…”，直到 `done`。顺带修掉时间线今天的同类问题：
   它现在在流未读完时会说“没有符合筛选条件的动作”。
2. **聚焦/结构仍归快照**：`action log` 行里没有关系边。流只解决“列表 + 色条 + done”，
   不解决“第 81 个 issue 的母/子/关系”——那一半仍是 §2 的详情端点。
3. **内存**：流本来就已经在浏览器里（时间线），issue 折叠只是多一个 Map；100k 的窗口化/宿主缓存
   是下一步的账，不是 issue 页新引入的问题。

### 3. 对 §3 的修订

- 原判：等 `list` 的 `date` + `limit/offset` 才能做索引。
- 新判：**列表数据来自流折叠**；`list` 退居“权威二次校验 / 大仓窗口”的备选。
- 上游缺口降级：`list --limit/--offset` 从“必须”变成“大仓优化”；`date` 不再必须（流里有）。
- 仍然缺的：`graph --issue` 的低成本实现（详情端点的成本瓶颈，见 §6）。

### 4. 落地顺序（修订）

1. 客户端从流折叠 issue 索引：列表、色条、done、筛选 gating；**无焦点**的 issue 页改用它；
   快照继续负责结构、关系边与聚焦态。（同时修时间线的假空态。）
2. 详情端点（`path` + `graph --issue`）解开快照外聚焦。
3. 一致性规则：**列表行只认流；结构/边只认快照**，同一处不混用；快照外的 issue 在无焦点列表里
   可展开动作，但聚焦仍走详情端点。

## 落地（2026-10-29）：无焦点的 issue 页改吃同一条流

按修订 §4 的第 1 步落地，不动详情端点：

- 宿主新增 `GET /kiln/actions`（`flow.js` 的 `readActions`）：`kiln action list --json` 的
  `names/start/terminal`，一次进程、不读历史；客户端按仓库缓存，重挂载不重取。
- 客户端 `foldIssues()`：首现=最近动作、`domain` 首个非空、`tags` 全量并集、
  `done`=最近动作 ∈ terminal、`ordinal` 在“看到 start”或 EOF 回填；`normalizeVocab()` 拦坏形状。
- 列表 = 流折叠 + 快照兜底：快照里已有的 issue 仍用快照字段（动作完整、带 `ordinal/refs`），
  流负责“多出来的那部分”；按 `last.date` 排序，首屏不空、EOF 也不会整体跳一下。
- 流里多出来的 issue：能展开完整动作链、色条随流增长；没有关系边 → 行尾显示「快照外」，
  不给聚焦按钮（与时间线同一规则）。
- 筛选：词表取不到时 `doneKnown=false`——不画 done chip，状态筛选也不把它算成 open；
  流没读完时筛选空结果显示「筛选中，继续加载…」，时间线同类假空态一并修掉。
- 快照截断提示只在关系页/聚焦态出现：全局 issue 列表已经不受 80 限制。

验证（2026-10-29，真仓 v0.3.0）：

- 折叠结果 vs `kiln list --json`：本仓 **23/23**、`~/kiln` **70/70**，
  `action / domain / done / title / tags` 全等，首现顺序严格 date-desc；
- 测试：**66 宿主 + 53 渲染**（新增折叠规则 3、issue 页 4、假空态 2，其余为既有用例）。

已知代价：

- 折叠是纯函数，每次流刷新重算全量（350 行是微秒级）；100k 行的窗口化/宿主缓存属于 §3 的下一步。
- 快照兜底意味着“快照知道的 issue 用快照字段”：生产上两者同源应完全一致，测试 fixture 里可以不一致。
- 快照外的 issue 仍不能聚焦（关系边不在流里）——那是 §2 详情端点的活。

## 非目标

- 不改时间线（`kiln action log --jsonl` 已定稿，这次不回头）；
- 不做落盘缓存 / 本地数据库；
- 不改搜索语义（`list --search` 的 rank / hit / 顺序仍归 kiln）；
- 不在这个 issue 里写实现；实现按结论另开 `apply`（或在本 issue 继续动作）。

## 验收（讨论出方向后）

- 四路输入各有一句结论：流式 / 分页窗口 / 保持整份（含“大仓降级”），并写明依据；
